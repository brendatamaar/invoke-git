# Task 025 handoff

Backlog task 25, the diff and graph half only: "Benchmarks with performance budgets, failing CI on regression". Row 25 in `docs/PLAN.md` is now "Core done".

## What changed

Branch `task-025-benches`, from `origin/main`.

- **`criterion` 0.8** is a workspace dev-dependency of `diff` and `graph` with `default-features = false, features = ["cargo_bench_support"]`. No rayon, no plotters (the lockfile gains 16 small crates: criterion, its plot-free helpers, clap, ciborium). `alloca`, a criterion dependency, compiles a small C shim, which the Windows and macOS runners can do; it could not be cross-checked from the VPS (`cargo clippy --target x86_64-pc-windows-msvc` stops at `lib.exe`), so see the CI result below.
- **`crates/diff/benches/diff.rs`** (group `diff`), all inputs generated from a fixed splitmix64 seed:
  - `histogram_50k_2k`, `myers_50k_2k`: 50k lines, 200 change clusters (5 modified, 2 deleted, 3 inserted lines each, about 2k changed lines), a third of the lines are braces and blanks.
  - `hunks_50k_2k`: rebuild the hunks of that diff with 10 lines of context (the viewer's "expand").
  - `word_pairs_1k`: `word_diff` on the 1,000 modified line pairs. `fill_inline_all_hunks`: `fill_inline` on every hunk.
  - `open_10k_lines`: the PRD case, a 10k-line diff plus the word diff of the first hunk.
  - Worst cases: `all_changed_50k` (no line survives), `repeated_10k` and `repeated_50k` (24 distinct lines, 10% re-rolled), `myers_repeated_50k`, `reversed_repeated_20k` (8 distinct lines, the file reversed).
- **`crates/graph/benches/layout.rs`** (group `graph`): 100k-commit histories built oldest first and reversed, so parents follow children. `layout_100k_linear`, `layout_100k_merging` (8 branches, a merge every 5 commits), `layout_100k_wide` (200 branches, a merge every 10; about 200 open lanes), `layout_100k_octopus` (the same plus a 12-parent merge every 50). Also `layout_page_5000_wide` (the first page, lanes building up) and `visible_window_60_wide` (`passing` + edges for 60 rows in the middle). The bench asserts the generated shapes (one lane; at least 4, 150 lanes; 12-parent merges) so a broken generator cannot pass silently.
- **`docs/perf-budgets.toml`**: one ceiling in ms per benchmark, each with its source. Absolute numbers from the PRD and specs, not baselines.
- **`cargo xtask bench-check`** (`xtask/src/bench.rs`): takes the shared check lock (so timings are not disturbed by another build on the VPS), clears its own criterion home (`target/bench-check`, via `CRITERION_HOME`, so stale results cannot pass), runs `cargo bench -p diff -p graph --benches`, reads the median of each `estimates.json`, and prints a table with headroom. It fails on a median past its ceiling, on a benchmark without a ceiling, and on a ceiling without a benchmark. The budgets file and the JSON are hand-parsed; 5 unit tests.
- **CI** (`.github/workflows/ci.yml`): a new job `Benchmarks (ubuntu-latest)` runs `cargo xtask bench-check`. See "Where it runs" below.
- **`DiffOptions::default().max_work` 50,000,000 to 10,000,000** (`crates/diff/src/model.rs`). Task 8's DONE left "task 25 calibrates it to 200 ms". At 50M the worst inputs took 470 to 520 ms here (past the 200 ms cancel budget), which the new worst-case benchmarks showed. One unit costs about 10 ns on this VPS; 10M gives about 100 ms for the worst inputs. Typical diffs spend under 1M (50k lines with 2k changes completes with a 1M limit; the 10k-line open case at 500k), so nothing real changes. The diff test suite passes unchanged.

The three worst cases that end in the work limit have the least room (about 2x), because the limit is itself calibrated to land near 100 ms; that is the point of the check (raise `max_work` or slow the engine and they fail). If a CI runner proves noisier than that, the proposed fix is to lower `max_work` to 5M (about 50 ms), not to raise the ceiling.

## Proof that the check can fail

Planted slowdowns, each run through `cargo xtask bench-check` (exit 1, the failing lines below), then reverted:

| Planted change | Result |
| --- | --- |
| `max_work` back to 50,000,000 | `FAIL diff/myers_repeated_50k: 405 ms is over the 200 ms budget`, `FAIL diff/repeated_50k: 407 ms ...`, `FAIL diff/reversed_repeated_20k: 508 ms ...` |
| `Layout::place` scans the open lanes 50 extra times per commit | `FAIL graph/layout_100k_wide: 816 ms over 320 ms`, `layout_100k_octopus: 809 ms`, `layout_page_5000_wide: 38.6 ms over 16 ms` |

Planted bugs in the xtask code, each caught by a unit test in `xtask/src/bench.rs` (script kept outside the repo history, in `target/`):

| Planted bug | Caught by |
| --- | --- |
| ceiling check loosened (`ms > budget * 2`) | `passes_within_budget_and_fails_past_it` |
| reads the mean instead of the median | `reads_the_median_not_the_mean` |
| a missing measurement passes | `a_missing_or_unbudgeted_benchmark_fails` |
| a benchmark without a budget passes | `a_missing_or_unbudgeted_benchmark_fails` |
| duplicate budget accepted | `rejects_bad_budget_files` |
| zero budget accepted | `rejects_bad_budget_files` |

`cargo xtask check` passes. A full `cargo xtask bench-check` takes about 1 minute on a warm VPS build.

## Anything surprising

- Histogram is about twice as slow as Myers on the typical 50k/2k input (37 vs 18 ms). Both are far under budget. The word diff and hunk building are cheap (a few ms).
- The default `max_work` was 5x too high for the 200 ms budget (see above).
- Wide histories (200 lanes) cost 5x more than linear ones, as the task 18 note predicted (linear scans of the open lanes), but stay at 20 ms per 100k commits.

## Spec questions with proposed answers

1. **No PRD number for graph layout, word diff or hunk building.** The ceilings for those are derived (one 16 ms frame, or the 50 ms first-lines budget; 20 pages for 100k commits). Proposed: keep the derivation in `docs/perf-budgets.toml`; add real numbers to the PRD budgets table if you want different ones.
2. **Where benchmarks run.** `docs/spec/verification.md` says "Build + full tests + benchmarks" on Windows every push. Proposed: keep the Linux job until a Windows timing is known, then move the step into the Windows job if it is under about 2 minutes there. Because the ceilings are absolute, the only change is the runner.
3. **Ceilings are generous on purpose** (2x to 200x headroom), so a runner 2x slower than this VPS does not fail the build. They catch complexity blowups and order-of-magnitude regressions, not 20% drifts. Proposed: once the reference laptop has been measured, tighten the graph and 50k diff ceilings to about 3x the laptop's number.
4. **`max_work` default** changed from 50M to 10M (spec: "past 200 ms is cancelled"; the spec has no unit). Proposed: keep 10M; the caller on the background thread may still map its own clock to a different work number.
