# Task 014 handoff

Backlog task 14, "Commit, amend, commit message editor" (Core + UI). This is the core half; row 14 in `docs/PLAN.md` is now "Core done".

## What changed

**Core (pure)**

- `crates/core/src/message.rs` (new): `CommitMessage::parse` (the one way a message enters), `normalize`, `split`, `subject_hint`, `strip_comment_lines`, the undo label.
  - Cleanup is git's `whitespace` mode, done by the core: CRLF and lone CR become LF, trailing whitespace goes, blank lines at the start and end go, runs of blank lines become one, one newline at the end. A `\r` never reaches a commit.
  - **Decision on `#` lines: kept.** git's default for `--file` is `whitespace`, which keeps them, and the editor has no template to strip (`#123 fix` must not lose its subject). Only a template git wrote (`MERGE_MSG`) is stripped, and only as the editor's starting text.
  - Refusal reasons (`MessageProblem`): `Empty`, `OnlyWhitespace`, `ContainsNul`.
  - `SubjectHint { chars, level }` with `Fine`, `PastSoft` (> 50) and `PastLimit` (> 72), counted in `char`s. Data only, never a refusal.
  - Undo label: `Commit 'Fix login'`, built from the first line of the cleaned message, cut at 60 `char`s on a char boundary with `…`, never multi-line.
- `crates/core/src/commit.rs` (new): `plan(disk, amend)` decides on the fresh snapshot.
  - Plain commit with nothing staged: `CommitRefusal::NothingStaged`. Unstaged and untracked changes do not count.
  - Amend: allowed with nothing staged (a reword); `AmendUnborn` on an unborn branch; detached HEAD is allowed.
  - Merging, no conflicts left: a plain commit is allowed with or without staged changes and is labelled `Conclude merge '...'`. With conflicts: `UnresolvedConflicts`. Amend: `AmendDuringMerge`.
  - Rebasing, cherry-picking, reverting: `Refusal::RepoBusy` (their own continue, task 23).
- `WriteRequest::Commit` now carries a `CommitMessage`. `step` parses it when `CommitRequested` arrives (a bad message is refused at once, no op id used); the rest is decided at dispatch. `GitArgs::Commit.message` is the cleaned text.
- `Refusal::Commit(CommitRefusal)`, `ErrorClass::Rejected` (new), `Irreversible::MergeConcluded` (new).

**Shell**

- `git commit` now also gets `--cleanup=whitespace`, so `commit.cleanup=strip` in a user's config cannot delete `#` lines.
- Hook failures (resolves `tasks/004.DONE.md` question 3): git prints nothing of its own when a hook fails and the hook can print anything (even `nothing to commit`), so output cannot identify it. A commit now runs with `GIT_TRACE2_EVENT=<temp file>`; `classify::failed_hook` reads the `child_start` (class `hook`) and `child_exit` events, matched by `sid` and `child_id`, for `pre-commit`, `prepare-commit-msg`, `commit-msg` or `pre-merge-commit` that exited non-zero. The result is `ErrorClass::Rejected` with details `The <hook> hook rejected the commit (exit code N).` followed by the raw output. A failing `post-commit` is ignored by git and stays a success. The trace file lives in the temp folder (never in `.git`), is capped at 8 MiB when read, and is removed afterwards.
- Missing identity: `Author identity unknown`, `Please tell me who you are`, `unable to auto-detect email address`, `auto-detection is disabled`, `empty ident name` are `ErrorClass::Environment`; for a commit the details start with `classify::IDENTITY_UNKNOWN` ("Git does not know who you are. Set user.name and user.email, then commit again."). `classify::is_identity_missing` lets the UI offer the fix.
- `read::head_message` (amend editor's starting text, cleaned, `None` on an unborn branch) and `read::merge_message` (`MERGE_MSG` without its `#` lines), both through gix and plain file reads, exported from `shell`.

**Tests**

- `crates/core/tests/message_props.rs` (13 tests, proptest), `crates/core/tests/commit_props.rs` (9 tests, proptest against an independent statement of the rules).
- `crates/shell/tests/commit.rs` (17 integration tests on temp repos), unit tests in `classify.rs` (hook trace parsing, ordering, identity).
- Updated fixtures: `step_props.rs` (`commit_round_trip` stages a file and expects the cleaned message), `undo_props.rs` (the simulated repo always has a staged file), `shell/tests/undo.rs` (`a_failed_commit_leaves_nothing_behind`: empty commit is now refused by the core, so the failing run there is a rejecting hook).
- The model-based harness already had `Commit { amend }` and stays green (model_based, self_check, laws registry); a commit refused by the core with nothing staged agrees with plain git failing.

## Spec questions (proposed answers)

1. **`#` lines and `commit.cleanup`.** `core-design.md` does not say. Decision above: keep `#` lines and force `--cleanup=whitespace`. Proposed: note it in the spec's shell section next to the `-c` rule, as an option on one command that keeps the committed text equal to the editor's.
2. **Merge commit is not undoable.** Restoring refs and the index after a merge commit would leave the merge's changes staged without `MERGE_HEAD`; committing them again would silently drop the second parent. I recorded it as `Irreversible::MergeConcluded` (an undo stops with a reason, as for a push). Proposed: keep, and later teach the undo to restore `MERGE_HEAD`/`MERGE_MSG` (that needs a saved copy in the undo point), then drop the marker. Law 8 says "every ref and the index"; `MERGE_HEAD` is neither, but the user-visible state is.
3. **Cherry-pick and revert conclusion.** `git commit` legitimately concludes a resolved cherry-pick or revert too. The task asked for the merge case only, so those phases are `RepoBusy` for now. Proposed: allow `ConcludeCherryPick` / `ConcludeRevert` kinds in task 23, with their own labels.
4. **How the editor gets its starting text.** Provided as two plain reads in the shell, not a `Command`/`Event`, to avoid inventing UI state. Proposed: when the UI task lands, add `Command::ReadDraft(DraftKind)` and `Event::DraftRead { kind, head, text }` (carrying the commit it was read from, so a text for an old HEAD is dropped), and keep the draft in the UI, not in `RepoState`.
5. **trace2 for hook detection.** It needs `GIT_TRACE2_EVENT`, which exists in every git >= 2.40, but I could only run it against git 2.43 here; CI covers Windows and macOS git. Proposed: if a git version names hooks differently, `failed_hook` returns `None` and the failure falls back to classification by output (so it would show as `Bug`, with the raw output). The core-design shell section should mention the env var next to `GIT_TERMINAL_PROMPT=0`.
6. **Subject counted in `char`s**, not grapheme clusters or display width (no crate for it in the PRD table). A subject of CJK or emoji is judged by scalar count. Proposed: revisit if the UI needs display width.
7. **Core-design `CommitRequested { message, amend }`** still holds a raw `String` (the editor's text): the cleaning happens in `step`. No spec change needed, but the spec could say the core owns the cleanup.

## Anything surprising

- The existing test `a_failed_commit_leaves_nothing_behind` relied on git failing with "nothing to commit". With the core refusing it first, nothing reaches git, so the test now covers both cases.
- A hook's own output can contain the very words the classifier looks for (`nothing to commit`, `CONFLICT`), which is why hooks are found through the trace and checked before the output markers (planted bug M15).
- Windows: hooks in the tests are `#!/bin/sh` scripts, which Git for Windows runs; the executable bit is set on Unix only.
- `--amend` keeps the author even when `GIT_AUTHOR_*` is set in the environment (git reads the old commit last), but the integration test uses the committer's identity from config as a real user would.
- `cargo fmt` rewrote nothing outside the touched files.
