## What changed

Branch `task-018-graph-layout`, from `origin/main`.

- **New crate `crates/graph`** (package `graph`), pure, no runtime dependencies. `proptest` is a dev-dependency only. No dependency on `core`, `gix` or the spike crates; the layout is generic over the commit id (`Copy + Eq`).
- `Layout<I>`: `push_page(&[Commit<I>])` (or `place` per commit) appends one `Row` per commit. The open-lane state lives in the layout, so the next page continues without recomputing (spec: "saves its lane state at the page edge"). `PAGE_SIZE = 5000` is exported for the shell.
- `Commit { id, parents, truncated }`: children first, first parent first. `truncated` marks a shallow-boundary commit: parents are ignored, the lane ends and the row is flagged for the faded stub.
- `Row` (16 bytes): column, colour index (0..8), merge flag, truncated flag, offset and counts into a shared edge arena, and width. Row `i` is the `i`-th commit pushed. Edges (`Edge { column, color }`, 4 bytes): arriving edges (every lane that waited for the commit, own lane included) then leaving edges in parent order.
- Lanes keep their column for life, so pass-through lanes are straight. They are not stored per row: `lanes_before(i)` and `passing(i)` rebuild them from a checkpoint (open lanes every 128 rows) plus at most 127 replayed rows.
- Colour: a lane gets the next palette colour (rotation of 8) when it opens and keeps it; the dot takes the colour of its leftmost arriving lane.
- **Tests** (`crates/graph/tests/layout_props.rs`, 5 proptests with 128 cases over random DAGs with parents outside the pages and shallow tips, plus 4 edge-case unit tests and one ignored timing test):
  - `edges_point_down_to_the_parent` (law 14): one row per commit, every leaving edge reaches its parent's row below, no dot sits on a lane that waits, the lane is in `passing` for each row between, colour kept, missing parents keep their lane to the bottom.
  - `paging_does_not_change_the_layout`: any page size gives identical rows, edges, lanes and checkpoints.
  - `replayed_lanes_match_the_live_lanes`: checkpoint replay agrees with the live lanes.
  - `waited_parents_stay_waited_for`: the Kani target "lane placement step" as a proptest; also step 4 joins an existing lane.
  - `dot_colour_follows_its_lane`: leftmost arriving lane, colour in range, width covers edges.
- **Planted bugs**, each applied alone and caught (script kept outside the repo):

| Planted bug | Caught by |
| --- | --- |
| Dot on the rightmost arriving lane | `dot_colour_follows_its_lane` |
| Closing lanes not freed | `waited_parents_stay_waited_for`, `replayed_lanes_match_the_live_lanes` and unit tests |

- **Timing** (release, VPS, `cargo test -p graph --release -- --ignored --nocapture`): 100k commits with a branch forking and merging every 10 commits: layout 22 ms; 100 `passing()` lookups 0.12 ms. This history keeps only a few lanes open. Cost is O(open lanes) per commit (linear scans), so a kernel-like history with hundreds of lanes is slower; criterion benchmarks on fixture repos belong to task 25.

## Anything surprising

- Spec questions with proposed answers:
  1. **Input order is trusted.** A parent arriving before its child, or a duplicate id, is not detected (that needs a set of placed ids, about 32 MB per million commits). Proposed: the shell's topo walk guarantees order and uniqueness; keep it out of the layout.
  2. **Arriving edge for the own lane.** The spec says only the other lanes "draw an edge into c's column". Here the own lane is also an arriving edge (straight), so the renderer knows whether to draw the top half (branch tips have none). Proposed: note it in the spec.
  3. **Shallow clones.** Spec says "parents beyond the boundary are missing". Here the shell sets `Commit.truncated` for boundary commits. A parent that is merely missing (not flagged) keeps its lane open to the bottom. Proposed: update the spec to name the flag.
  4. **Lane count above 65,535** saturates the column at `u16::MAX`; the spec's row record uses `u16`, so this is the stated limit.
  5. Edge colour for a joined lane is the target lane's colour; for a new lane, the next rotation colour.
- Property tests take about 15 s in debug because `passing()` is checked for every row between an edge's ends.

## Renderer and shell walk (added 2026-11-22, branch `task-018-graph-renderer`)

- **`shell::history`** (gix only, no lock): `walk(paths, limit, cancel)` streams `graph::Commit<CommitId>` pages of 5,000 from a thread. Starting points are `HEAD`, `refs/heads`, `refs/remotes` and `refs/tags` (tags peeled to commits), topological order, commit-graph file when present. A shallow repo (`.git/shallow`) cannot use gix's topological walk (it looks for the boundary's missing parents), so it is ordered by Kahn's algorithm with the boundary commits as roots and flagged `truncated`. `read_meta(paths, ids)` reads subject, author and time for a batch; an unreadable commit is `None`.
- **`ui`:** `GraphView<I>` (generic over the commit id, so `ui` does not depend on `shell`), `ref_labels` (current branch first, then local, remote, tag; the remote `HEAD` alias is left out), `time` (`relative` and `format_date`), a `+N` marker with its own room, and `RepoSummary::control`.
- **`app`:** `HistoryPane` owns the walk task. It starts on the first visit to History, feeds pages to the view, answers `NeedMeta` with a background `read_meta`, and restarts the walk with the old graph kept on screen when `HEAD` or any ref changes. `RepoView` has a Changes and History switch.
- **Tests:** `shell/tests/history.rs` (9, one a proptest over random histories, with `git rev-list --parents --all` as the oracle: every commit once, the parents, children before parents, a tag-only commit, an unborn repo, a shallow clone, cancel, metadata against `git log`), `ui` 48 (new: time 5, ref labels 3, graph column width 2). **Planted bugs, all caught:** tags not used as starting points (`a_commit_only_a_tag_reaches_is_walked`, `every_commit_once_...`), shallow boundary keeps its parents (`a_shallow_clone_flags_its_boundary`), current branch not flagged (`labels_group_by_commit_and_current_comes_first`), hours read as minutes (`reads_like_the_mockup`), no room for the `+N` marker (`the_graph_column_grows_with_the_lanes_up_to_the_cap`). One plant survived because it was dead code (`truncated` in the non-shallow loop); I removed it.
- **Measured on the kernel clone** (`cargo test -p shell --release --test history -- --ignored --nocapture` with `INVOKE_GIT_BIG_REPO`): 1,507,472 commits, first page after 1.8 s, walk and layout done after 3.2 s, layout alone 0.5 s. In the app the whole history was in memory at about 390 MB (working set), 80 MB before opening History.
- **I ran it on this laptop** (fixture repo with branches, merges, a tag and a remote; and the kernel clone), with synthetic input and screenshots: lanes and curves, hollow merges, the accent ring on HEAD, the pills (current branch accent, remote outlined, tag dashed), relative dates, and a scrollbar drag through the kernel history with rows coming up at once. My own check, not a claim that it works for you.

### Windows checklist

`cargo run --release -p app -- C:\path\to\a\repo`, then click **History**.

1. A header row (GRAPH, SUBJECT, AUTHOR, DATE, HASH) and one row per commit, newest first; lanes are coloured lines; a branch point and a merge show curves; merges are hollow dots; the current commit has a ring in the accent colour.
2. Before each subject: `main` in the accent pill (bold), other local branches in a raised pill, `origin/...` outlined, tags dashed.
3. Dates read `12 min ago`, `Yesterday`, `4 days ago`, then `YYYY-MM-DD`. Hover a row: its lane stays bright and the others fade.
4. Click a row: it is highlighted and its dot turns accent.
5. In a repo with 100,000 or more commits, drag the scrollbar from top to bottom several times: rows must come up at once (subject and date may appear a moment after the graph), no flash, no crash. Check memory in Task Manager.
6. Make a commit or create a branch in another terminal while History is open: within about a second the new commit appears and the scroll position stays on the same commit.
7. Open a shallow clone (`git clone --depth 2 ...`): the oldest commit's lane ends in a short faded stub.
