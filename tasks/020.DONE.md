## What changed

- **Core (pure).**
  - New `crates/core/src/stash.rs`: `StashEntry { id, message }` (the id is the stash commit), `position`, `top`, `clean_message`, `label`.
  - `DiskState.stashes` (newest first). Requests: `Event::Stash{Save,Apply,Pop,Drop}Requested`; `WriteRequest::Stash*`; `GitArgs::Stash*` (apply, pop and drop carry both the position and the commit id); `Action::Stash*`; `Refusal::StashGone(id)`.
  - Planning happens at dispatch, against the fresh snapshot the write runs on (like undo): the id is looked up in the list, and a stash that is not there is refused (`StashGone`) with no write. Save, apply and pop are also refused with `RepoBusy` during a merge, rebase, cherry-pick or revert; a drop only touches the stash list and is allowed.
  - Undo points (decision, see below): every stash op takes a point through the existing `SnapshotForUndo` flow. `UndoPoint.reverse: Reversal` is `Refs` (commit), `StashStore(entry)` (drop of the newest stash), `StashKept(entry)` (drop of an older stash) or `Never(Irreversible)`. New `Irreversible::{StashRewroteFiles, StashNotOnTop}`. `UndoReplay.stash: Option<StashRestore>` makes a replay put the dropped stash back instead of restoring refs and the index.
  - A running stash op ignores `OpCancelRequested`; queued ones can still be cancelled.
- **Shell.**
  - `read_state` reads the stash list from the `refs/stash` reflog through gix (`read::read_stashes`, forward then reversed, because the reverse reader uses a fixed 4 KiB window).
  - `git::invocation`: `stash push [--include-untracked] [--message=<m>]`, `stash apply|pop|drop stash@{n}`. The message is one argv element that starts with `--message=`.
  - `precondition::check_stash` (called by the runner before every apply, pop and drop): re-reads the list and refuses with `PreconditionChanged` if the entry at `n` is not the expected id.
  - `classify`: pop/apply conflicts (`CONFLICT`) were already Expected; added git's "local changes would be overwritten", "already exists, no checkout", "No stash entries found", and others. `classify_stash_save` turns git's exit-0 "No local changes to save" into an Expected failure.
  - `UndoRunner`: `snapshot` also keeps the stash commit alive under `refs/invoke-git/undo/<op>-stash` for drops; `replay` of a stash restore checks the list's newest entry and runs `git stash store`; `prune` deletes both refs.
- **Tests.** Core `stash_props.rs` (11 tests; 2 more unit tests in `stash.rs`), `step_props.rs` extended (stash events and a random stash list in the generators). Shell `tests/stash.rs` (16 integration tests on temp repos with real git as the oracle), plus argv and classify unit tests. Existing literals in `tests/undo.rs`, `undo_props.rs` and `step_props.rs` got the new fields.
- `cargo xtask check` passes.

### Decisions

1. **Drop is undoable only when it is the newest stash.** The dropped commit is kept alive under `refs/invoke-git/undo/<op>-stash` for every drop, so no work is lost either way. Undo runs `git stash store -m <message> <id>`, which puts it on top. For an older stash that would not restore the list exactly (law 8), so the entry is on the stack as not undoable (`StashNotOnTop`); the commit is still kept.
2. **Save, apply and pop are not undoable.** They rewrite working files, which undo does not do (spec: only a discard's undo does, task 13). They still go on the stack as `Irreversible::StashRewroteFiles`, so an undo stops with that reason instead of reversing an older commit behind them. The stash entry is the way back.
3. **A failed or conflicted op records nothing**, like a failed commit. After a conflicting pop the next undo hits the older point and refuses on the changed index.
4. **Running stash ops cannot be cancelled** (law 13): `git stash push` saves the stash and then resets the worktree; a kill in between leaves both.

## Anything surprising

- **A conflicted pop leaves `Phase::Clean`.** git's stash pop writes unmerged index entries but no `MERGE_HEAD`, so the repo-state detection (task 5) reports `Clean` with conflicts only visible as index stages. The conflict flow (task 11/22 UI) needs those paths to open. Question: should `Phase` get a stash-conflict variant, or should the status tree (task 11) list unmerged paths regardless of phase? Proposed: the status tree lists unmerged paths regardless of phase; no new phase.
- `git stash push` with nothing to save exits 0, so exit status alone would call it a success.
- The reverse reflog reader in gix uses a fixed window; the list is read forward and reversed.
- A refused request leaves an older notice of the same action on screen when a later request of that action is accepted. The existing `requests_are_queued_or_refused` property assumed otherwise; it now only counts a notice that changed in that step. Proposed: a UI-level decision (clear notices on accept?).
- The shared scratchpad is shared between parallel agents: another agent overwrote my mutation script once, and my shell mutation run briefly ran their script against their worktree before I noticed. Mine now has a unique name.

## Spec questions, with proposed answers

1. **Apply and pop without `--index`** (git's default): staged state is not restored exactly, and newly added files stay staged. Proposed: keep git's default, because `--index` fails on index conflicts.
2. **Drop undo puts the stash on top**, so only the newest stash is undoable (decision 1). Proposed: accept, and let the UI warn before dropping an older stash.
3. **Persistence of undo across restart** is still the open question 1 from task 12; the stash keep-alive refs follow the same rules (orphans are not pruned on restart).
4. **Cancel of stash ops** is not offered (decision 4). Proposed: the UI hides Cancel for stash operations.

### Windows checklist (tasks 2, 7, 10, 11, 14, 15, 18, 19 apply too)

Use a throwaway repo: one modified tracked file, one new untracked file. `cargo run --release -p app -- C:\path\to\repo`.

1. The sidebar header reads `BRANCHES  Stash  + Branch` without clipping, at 100%, 150% and 200% scale.
2. `Stash`: a form with a message field, `Include untracked files` (unticked) and a hint. With no changes at all, `Stash changes` is disabled and the hint says so.

8. `Drop`: a question appears; `Cancel` keeps the stash; `Drop stash` removes it and the header shows `Undo  Drop stash ...`; Undo brings it back as the newest entry. With two stashes, `Drop` on the older one says it cannot be undone.

10. A pop that conflicts: the files show conflict markers and the list shows them as changed; nothing is lost (resolving is task 23).
