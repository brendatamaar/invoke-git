# Task P0-2 handoff

Phase 0 task P0-2: Prototype A, the diff view in `spike-diff`.

## What changed

Branch `p0-2-diff-view`, based on `p0-1-spike-scaffold` (P0-1 is not merged yet).

- **New dependencies (spike only):** `imara-diff` 0.2.0, `tree-sitter` 0.27.2, `tree-sitter-rust` 0.24.2, and `streaming-iterator` 0.1.9 (tree-sitter 0.27's capture iterator is a `StreamingIterator`; tree-sitter already depends on it).
- **`model.rs`:** reads both files on a background thread, splits them into line ranges, runs a histogram diff (`imara-diff`, with its line post-processing), and aligns the hunks into split rows. Context goes on both sides; removed lines are paired with added lines by position; filler fills the shorter side.
- **`highlight.rs`:** parses each whole file with tree-sitter on a background thread, then runs the Rust highlight query per 128-line chunk (`set_byte_range`). Captures are clipped to lines and kept disjoint. Captures map to tokens: keyword → `accent`, string → `add-ink`, comment → `ink-faint`, type → `lane-2`, function → `lane-7`, number → `warning`.
- **`view.rs`:**
  - Rows render in a `uniform_list` on 20 px rows, using Cascadia Mono 13 px for code and 12 px for line numbers.
  - Each side shows old and new line numbers, `−`/`+` signs and `remove-bg`/`add-bg` backgrounds, with `bg-app` filler.
  - Highlight chunks are requested for the visible rows ±200 lines and cached per side. Rows render plain until their chunk is ready.
  - A custom scrollbar can be dragged end to end; clicking the track jumps there. Dragging keeps working outside the window while the button is held.
  - The header shows the file names, the +/− counts and the measurement readout. Clicking the readout resets it.
- **`stats.rs`:** tracks fps, frame-interval p95 and max, frame-build p95 and max (render start to end of paint), worst interval, frames over 50 ms, blank rows, unstyled rows and first paint. A summary is logged every 5 s.
- **`main.rs`:** usage is `spike-diff [--sweep SECONDS] [OLD NEW]`; without paths it opens the fixtures. `--sweep N` scrolls top to bottom at constant speed once both parses finish, prints the stats and quits. This gives a repeatable worst case for P0-4.
- **Tests:** 8 unit tests (row alignment, line splitting, token mapping, disjoint spans, chunk offsets, p95, the stats window). Each was shown to fail by a mutation:
  - Pairing every added line with the hunk start.
  - Mapping functions to types.
  - Removing the overlap guard. This first survived, so I added `Some(2)`, which is captured twice.
  - Using the max instead of p95.
- `cargo xtask check` passes: fmt, clippy with no warnings, and all tests.
- `docs/spike-results.md` records the preliminary numbers and GPUI notes.

**Preliminary results** (on battery, so not valid for the gate; details are in `docs/spike-results.md`):
- First paint: 79–115 ms after data ready.
- Fast and slow sweeps: 58–60 fps, 0 blank rows, 0 frames over 50 ms, build p95 11–18.6 ms.
- Full parse: 0.7–1.4 s per side.

**Spec gaps and questions:**

1. **The parse-time fallback would disable highlighting for these fixtures.** `diff-engine.md` → Highlighting pipeline, step 6, says a parse slower than 100 ms renders as plain text. Tree-sitter needs about 700 ms for each 1.5 MB fixture on this CPU, even alone and in a release build. **Proposed answer:** drop the parse-time fallback. Render plain until the tree arrives, as the spike does; it costs nothing visible. Keep only the size threshold (5 MB or 100k lines).
2. **The in-app frame-interval p95 can't decide the gate.** At idle it reads 22–25 ms while the window paints a steady 60 fps, because paint timestamps jitter against vblank: GPUI presents with `Present(0)` from a `DwmFlush`-paced thread. **Proposed answer:** measure the gate with PresentMon, an open-source tool from Intel/GameTechDev that records per-process present and display times. It is a separate install, so I need your OK first. Fallback if you'd rather not install it: pass on fps ≥ 59 over each 5 s window, build p95 ≤ 16.7 ms, no frame over 50 ms, and no visible stutter by eye.
3. **Does diff time count toward first paint?** The plan defines data ready as "both files loaded", so index, diff and rows (35–50 ms) count against the 100 ms. **Proposed answer:** yes. Keep it strict, since the real app also diffs after loading.
4. **Numbers and booleans share a capture.** tree-sitter-rust tags integer, float and boolean literals all as `@constant.builtin`, so `true`/`false` are coloured `warning` too. **Proposed answer:** accept it for the spike. The real theme layer (backlog task 9) can split them with its own query.
5. **The modified fixture is not valid Rust.** `new.rs` parses with 782 error nodes, because the generator's edits break syntax. Highlighting still works, but error recovery makes the parse slower. **Proposed answer:** keep it as a stress case.

## Anything surprising

- **A custom scrollbar was needed.** GPUI core at this revision has no scrollbar (Zed's `ui` crate does). Writing one was easy with `UniformListScrollHandle` and `window.on_mouse_event`.
- **CPU cost is per frame, not per new row.** Slow and fast sweeps cost about the same (build p95 11–18 ms). The cost is laying out and painting about 45 rows × 9 divs each frame, not shaping text. A custom element per row, or for the whole viewport, is the obvious optimization if P0-4 sees drops. The PRD already says "own GPUI elements" for the diff viewer.
- **tree-sitter 0.27 hides `QueryMatch.captures`** behind a `captures()` method, and its captures iterator is a `StreamingIterator`. Older examples online don't compile.
- **First paint is about half GPUI's first content frame.** Data reaches the UI thread at 33–50 ms; the rest (about 45–65 ms) is GPUI building and painting the first full list frame.
- **Diffing the 50k-line files takes 21–34 ms** with `imara-diff`'s histogram algorithm. That is fine for a spike, but it already uses a third of the first-paint budget.
- **The laptop was on battery** during every run (status "discharging", 37 %). Numbers will likely improve when plugged in.

## Windows checklist for UI changes

Plug the laptop in and close heavy apps. From the repo root in PowerShell:

1. `git switch p0-2-diff-view`
2. `cargo xtask fixtures` (if `fixtures/diff/` is missing)
3. `cargo run --release -p spike-diff`
   - [ ] A window titled **spike-diff** opens at about 1400×900, with a 40 px header showing `old.rs → new.rs`, a green `+1709`, a red `−1605`, and the readout on the right.
   - [ ] Below it, two code columns with a thin divider, in a monospace font (Cascadia Mono), on near-black panels.
   - [ ] Each side has grey line numbers on the left. Changed rows show a red `−` and a dark red background on the left, or a green `+` and a dark green background on the right. Where a hunk is shorter on one side, the filler is darker (`bg-app`).
   - [ ] Within about 1–2 s, syntax colours appear: keywords in indigo, strings in green, comments in grey, types in teal, functions in blue, numbers in amber.
   - [ ] The console prints the timings line, `first paint … ms`, the two `parsed … side` lines, then a stats line every 5 s.
4. Wheel scrolling:
   - [ ] Scroll quickly for about 10 s. Text stays crisp, there are no blank or half-drawn rows, and the readout's `blank` stays 0.
   - [ ] Colours appear on newly visible rows with no visible flash of plain text during normal wheel scrolling.
5. Scrollbar:
   - [ ] A 12 px scrollbar sits on the right, and its thumb moves while you wheel-scroll.
   - [ ] Drag the thumb from top to bottom three times. The list follows the pointer all the way to line 50,000 and back, and keeps following if the pointer leaves the window while the button is held.
   - [ ] Clicking the empty track jumps there.
6. Readout:
   - [ ] Click the readout and confirm the console prints `stats reset`.
   - [ ] After 10 s of scrolling, note fps and `build p95` and send me the console output.
7. Automated sweep: run `cargo run --release -p spike-diff -- --sweep 20`.
   - [ ] It scrolls by itself from top to bottom in about 20 s, then the window closes and the console prints `sweep done …`. Send me that output too, since it is a plugged-in comparison with my battery runs.
8. Task Manager while scrolling:
   - [ ] Peak memory is around 200–250 MB.
