## What changed

Branch `task-023-conflicts`, from `origin/main` at `8126f88`.

- **core `conflict.rs` (new):** the flow as enums. `Operation` (`Merge`, `Rebase { step, total }`, `CherryPick`, `Revert`; the step is part of the identity), `ConflictKind` (the seven combinations of index stages 1, 2, 3 present), `FileState::{Unresolved(kind), Resolved}`, `Conflicts` (sorted, unique, built with `Conflicts::from_parts`; an Unresolved entry wins over a Resolved one for the same path), `ContinueGate::{NotInProgress, Blocked { unresolved }, Ready}` and `continue_gate(&Phase)` for the UI's button, `ResolveChoice::{Ours, Theirs, Manual}`, `ConflictRefusal`, the planners `plan_continue`, `plan_skip`, `plan_abort`, `plan_resolve`, and the data the resolver shows: `ConflictContent { base, ours, theirs }` of `StageContent::{Absent, Text, Binary { size }}`. `Phase::operation()` and `Phase::conflicts()` accessors.
- **core state:** `Conflicts` moved out of `state.rs` (re-exported; it no longer has a public `paths` field). `Refusal::Conflict(ConflictRefusal)`, `Action::{ResolveFile, Continue, Skip, Abort}`, `Irreversible::Continued`.
- **core requests:** `Event::{ResolveFileRequested { path, choice }, ContinueRequested, SkipRequested, AbortRequested}`, `WriteRequest::{ResolveFile, Continue, Skip, Abort}`, `GitArgs::{ResolveTakeSide, ResolveRemove, ResolveStage, Continue, Skip, Abort}`. Continue, Skip and Abort carry the operation the user saw (taken from the snapshot at request time); everything is planned again against the snapshot the write runs on, so a request for rebase step 2 is refused on step 3 (a double click cannot skip two commits) and Continue is refused unless every file is Resolved right now.
- **core `step.rs`:** Continue leaves an irreversible undo marker (`Continued`); resolve, skip and abort take no undo point (see "Surprising"). A running conflict operation is not cancelled (like stash), so an abort is never killed half way (law 13). Push and Fetch are now refused with `RepoBusy` while an operation is paused (Pull already was): the conflict screen says they are paused, and a paused rebase must not be pushed.
- **shell `git.rs`:** argv for `<merge|rebase|cherry-pick|revert> --continue|--abort`, `rebase --skip`, `--literal-pathspecs checkout --ours|--theirs -- <path>` then `--literal-pathspecs add -- <path>` (`invocations()` returns the two runs), `rm --force --quiet -- <path>` for a missing side, and `add -- <path>`. Paths are literal (a file named `x[ab].txt` does not take `xa.txt` with it).
- **shell `runner.rs`:** a request runs its `invocations()` in order and stops at the first failure. For Continue, Skip and Abort the runner sets `GIT_EDITOR=true` and `GIT_SEQUENCE_EDITOR=true` **after** the user's and the extra environment, so git never waits for an editor and no inherited editor can come back. This is the environment addition the brief asked to record.
- **shell `read.rs`, `resolve_undo.rs` (new):** unresolved files and their kinds come from the index stages; resolved files from the index's resolve-undo (`REUC`) extension, read from the raw index file only while something is in progress. See "Decisions".
- **shell `conflict.rs` (new):** `read_conflict_content(paths, path)` returns base, ours and theirs from the index stage blobs through gix; text is kept byte for byte (CRLF stays CRLF), NUL bytes or invalid UTF-8 are `Binary { size }`, a missing side is `Absent` (delete/modify, both added), a submodule stage is `Binary { size: 0 }`.
- **shell `classify.rs`:** `Could not apply`, `unmerged files`, `You must edit all merge conflicts`, `No changes - did you forget to use 'git add'`, `There is no merge to abort`, `No rebase in progress`, `no cherry-pick or revert in progress`, `There is no merge in progress` are `Expected`.

- **Tests:** core `conflict_props.rs` (15: proptests and unit tests), `step_props.rs` generates the four new events (so every existing generic property covers them); shell lib +15 (argv unit tests and two proptests, resolve-undo parser, content classification, classify cases); `crates/shell/tests/conflicts.rs` (21 integration tests, real core driving the real shell on temp repos); `read_state.rs` updated (a resolved file now reads as Resolved).

## Decisions (spec gaps; proposed answers, implemented)

1. **"Resolved by editing but not staged."** A file is Resolved exactly when git says so: stage 0 is back in the index. A file edited in the worktree but not staged is still Unresolved (and `git rebase --continue` would refuse it too). "Mark file resolved" in the UI is `ResolveFileRequested { choice: Manual }`, which stages the worktree file as it is, so the UI writes the merged text first. `Manual` is also allowed on an already Resolved file (edit again, stage again) and is how a file deleted by hand is resolved (`git add` of a missing path stages the deletion).
2. **Where Resolved comes from.** Staging removes a file from the unmerged set, and nothing else on disk says it was ever conflicted except the index's resolve-undo record (what `git ls-files --resolve-undo` prints). gix decodes it but does not expose it, and the git CLI is not for reads, so `shell/src/resolve_undo.rs` reads the extension from the raw index file with std only. The extension has no fixed offset; a `REUC` signature counts only when the chain of extensions starting there ends exactly where the checksum begins, so a file named `REUC...` in the entries cannot be mistaken for it. It is advisory: if it does not parse, files show as Unresolved or drop out of the list, never as wrongly Resolved. It is only read while a merge, rebase, cherry-pick or revert is in progress. Checked on real git: it does not linger across rebase steps (step 2 starts with an empty Resolved list), and it is dropped by the commit.
3. **Ours and theirs.** `Ours` is index stage 2 (what `HEAD` has) and `Theirs` is stage 3, as in git. In a rebase `HEAD` is the branch being rebased onto, so "ours" is the upstream and "theirs" is the commit being replayed; the UI's "Accept current" is `Ours` and "Accept incoming" is `Theirs` in every operation, which is what the labels mean on screen.
4. **A side that does not exist.** In a delete/modify conflict, taking the side that deleted the file resolves by removing it (`ResolveRemove`), planned in the core from the conflict kind. Taking the side that kept it checks it out and stages it.
5. **Skip is for a rebase only** (the PRD table). `git cherry-pick --skip` and `git revert --skip` exist, but the spec does not list them; refused with `SkipNotAvailable`.
6. **Push and Fetch are refused while paused** (`RepoBusy`), matching the conflict screen's banner and the PRD's "a paused rebase cannot be pushed". The PRD's allowed-actions table does not list them for any paused state. If a fetch during a merge should stay allowed, delete the guard in `step.rs` (one `if` each).
7. **The flow opens from the snapshot.** A pull or continue that stops on a conflict ends `Failed(Expected)` and its notice is an ordinary `OpEnded`; the UI shows the conflict screen because `DiskState.phase` is not `Clean`, never because of the notice (rule 4).

## Anything surprising

- **No undo point for resolve, skip and abort.** `SnapshotForUndo` saves the index with `git write-tree`, which fails while any file is unmerged, so these writes cannot take a point at all. Abort is git's own exact way back (law 8 is checked by comparing refs, `HEAD`, `ls-files -s`, status and every file before and after), and a resolve is undone by resolving again or aborting. Only Continue (all files Resolved, so `write-tree` works) leaves a marker, `Irreversible::Continued`, so an undo explains itself instead of silently reversing an older commit; an older undo entry refuses by itself because the refs moved.
- **An empty resolution in a rebase** (taking `main`'s side for a commit whose change `main` already has) does not fail: git drops the commit when continuing and goes on. The "No changes" classification is kept for older git versions but I could not make git 2.43 print it.
- `git checkout --ours -- <untracked path>` fails but `git checkout --ours -- <tracked, not conflicted path>` succeeds as a no-op, so the second run (the stage) matters: a test makes sure the stage does not run after a failed checkout.
- The agent shell has `GIT_EDITOR=true` in its environment, which hid the editor problem: the first mutation of the env addition survived. The fixture now sets `GIT_EDITOR=false`, `GIT_SEQUENCE_EDITOR=false` and a global `core.editor = false`, and the runner sets its editor variables last.
- `Conflicts` is no longer a plain struct with `paths`. Other branches that build one with `Conflicts { paths }` must use `Conflicts::from_parts(unresolved, resolved)`.
