# Task 003

## Goal

Create the pure `core` crate with the repo-state types (`RepoState`, `Event`, `Command`) and a `step()` skeleton. The skeleton holds the shared machinery that later tasks build on:

- disk changes are always re-read, and never patched from memory
- reads are applied in order
- there is one write at a time, and writes wait for a fresh snapshot and a free `index.lock`
- each write command carries the values it expects to find on disk
- long operations follow one lifecycle (running, auth prompt, cancelling, finished)

## PRD law numbers

The skeleton enforces the core half of these laws. Their owning tests are model-based or integration tests and come with tasks 4, 6 and 24:

- 11: `DiskChanged` only emits `ReadState`, and only the newest `StateRead` replaces the snapshot.
- 12: no write command is emitted unless the snapshot is fresh and its lock is `Free`.
- 13: every finished or cancelled operation is followed by a full `ReadState`.

## Constraints

- `core` is pure. It does no filesystem, network, clock, thread or randomness work, and has no runtime dependencies. Ids come from counters inside the state.
- Logic has the shape `step(state, event) -> (state, commands)`. The `step` function never panics on any input.
- Phases and lifecycles are enums, not booleans.
- Each write command carries what it expects to find on disk (head and index id).
- `proptest` is the only new dependency, and only as a dev-dependency. It is in the PRD's build-vs-library table.
- Only add request handling that is part of the skeleton. Stage, unstage, push and undo are refused with a stated reason until their own tasks (11, 17 and 12) add them. Commit dispatches, because one real write is needed to exercise the queue.

## Acceptance criteria

- `cargo test -p invoke-core` passes, including property tests over random event sequences for:
  - `step` never panics
  - `DiskChanged` never changes the snapshot
  - the newest read wins, and an out-of-order older read never regresses the snapshot
  - write commands are emitted only on a fresh, unlocked snapshot, carry its expected values, and have at most one write in flight
  - every request is either queued or refused for a stated reason
  - every finished operation is followed by a full re-read
- Each property test is shown to fail once by breaking the code on purpose. The results are recorded in DONE.md.
- `cargo xtask check` passes on the VPS.
