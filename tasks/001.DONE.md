# Task 001 handoff

Backlog task 1: Cargo workspace, CI, license, README.

## What changed

Branch `task-001-ci`, based on `p0-4-gate` (the Phase 0 branches are not merged yet).

- **`.github/workflows/ci.yml`:** runs on every push and on manual dispatch. A newer push to the same branch cancels the running build.
  - **Windows (everything):** `windows-latest`, `cargo xtask check` (fmt, clippy with `-D warnings`, tests for every crate, GPUI included), 90-minute timeout.
  - **Core:** `ubuntu-latest` and `macos-latest`, `cargo xtask check --core`, 30-minute timeout, `fail-fast: false`.
  - Rust comes from the runners' own rustup (`stable`, minimal profile, rustfmt and clippy). Only GitHub's own actions are used (`checkout@v4`, `cache@v4`).
  - The Cargo registry, git database and `target/debug` are cached per OS and keyed on `Cargo.lock`.
- **`cargo xtask check --core`:** skips `ui`, `app`, `spike-diff` and `spike-graph` on any machine and prints that it did. Before this, they were skipped only on headless Linux, so a macOS runner would have built GPUI. A bad flag prints the usage and fails.
- **`README.md`:** CI badge, a CI section with the job table, the `--core` flag, and the `--commit-box` run line.
- **Checked locally on Windows:**
  - `cargo xtask check --core`: passes, and skips the four UI crates.
  - `cargo xtask check`: passes, all 23 tests.
  - A bad flag is rejected.
- **Already done before this task:** workspace (P0-1), `LICENSE` (Apache-2.0), README with the GPUI pin (P0-1), `cargo xtask check` (`57f072f`).

## What is unfinished

The likely things to fix after the first run are the cache size (the Windows `target/debug` is about 2.2 GB) and the cold build time.
- **The backlog status in `docs/PLAN.md` is unchanged.** I'll mark row 1 done once CI is green.

**Spec gaps and questions:**

1. **Is a scheduled warm-up job needed?** The Windows job does a cold GPUI build (about 11 minutes on the laptop, probably slower on a runner) whenever the cache misses, which happens whenever `Cargo.lock` changes. **Proposed answer:** accept it for now. If it hurts, add a scheduled job that keeps the cache warm.
2. **The core jobs still fetch the Zed repository.** Cargo resolves the whole lockfile even when GPUI crates are excluded, so it downloads the pinned Zed git repo (about 1.2 GB in `~/.cargo/git`). Only the git database is cached, not the checkouts. **Proposed answer:** accept it. Once the real `ui` crate exists, consider keeping GPUI out of the core jobs' resolution, for example with a separate workspace for UI crates. That is a bigger decision, so I'm not doing it here.
3. **CI on pull requests.** CI runs on pushes only, not on `pull_request`, to avoid duplicate runs for same-repo branches. **Proposed answer:** keep it until there are outside contributors.
