# Task 012 handoff

Backlog task 12: Undo system (reflog and index snapshots). Branch `task-012-undo`, from `origin/main` at `2ba7289`.

## What changed

- **Core (pure).** New `crates/core/src/undo.rs`: `UndoStack` (bounded at `MAX_POINTS` = 50, oldest dropped and pruned), `UndoEntry`, `Reversible`/`Irreversible` (a push stays on the stack as "not undoable" so an undo stops with a reason instead of skipping it), `UndoPending` (enum lifecycle: `Recording`, `Taken`, `Settling`, `Replaying`, `Rewinding`), `plan()`.
  - `RepoState.undo`; `WriteRequest::Undo`; `Event::UndoSnapshotTaken`; `Command::ReplayUndo(UndoReplay)` and `Command::PruneUndo`; `UndoPoint` gains `head: HeadTarget`.
  - `UndoRequested` is refused at once when the stack is empty or the top point is irreversible; otherwise it is queued like any write. At dispatch (fresh snapshot, lock free, one write at a time) it is planned against that snapshot and refused with `Refusal::{NothingToUndo, NotUndoable, RepoBusy, Changed(Head|Ref|Index)}` unless the head target, every recorded ref and the index are exactly where the operation left them. A refused undo no longer blocks the queue (`dispatch` loops).
  - A point becomes an entry only after the operation succeeded and the next fresh read showed what it left behind (`Settling`). A failed or cancelled operation drops its point and prunes its saved tree. After a successful undo the new top entry's index id is re-based on the next fresh read (see questions).
  - `PruneUndo` is not `is_write`: it touches only our own `refs/invoke-git/undo/*`.
- **Shell.** New `crates/shell/src/undo.rs`, `UndoRunner`:
  - `snapshot(point)`: checks the index id, copies the index file, runs `git write-tree` with `GIT_INDEX_FILE` on the copy (plain `write-tree` rewrites the real index and changes its id, which would make the operation's own expected index stale), keeps the tree alive with `git update-ref refs/invoke-git/undo/<op>`. Returns `Snapshotted::Taken(event)` or `Failed(OpFinished)`; on `Failed` the driver must not run the operation.
  - `replay(plan)`: `precondition::check` (head and index), one `git update-ref --stdin` transaction with every ref's current value as the expected value, then `git read-tree <tree>`; if read-tree fails the refs are rolled back.
  - `prune(ops)`.
  - Nothing is wired into an app loop yet (none exists); the integration test `Driver` shows the intended wiring.
- **Tests.** Core: `crates/core/tests/undo_props.rs` (4 tests; a simulated shell and repo plus an independent twin oracle over random commit/undo/outside-change/branch-switch/lock sequences, 256 cases of up to 200 steps), `step_props.rs` extended (`UndoSnapshotTaken` events, `ReplayUndo` checks in the write-law test, a bound test, the round trip now also covers recording and planning an undo). Shell: `crates/shell/tests/undo.rs`, 12 tests on temp repos with real git as the oracle, owning law 8 (commit, amend, first commit, chained undos) and law 9 (no other ref moves), plus refusals after an outside commit, an outside index change and a branch switch, a failed commit, snapshot keep-alive, and replay atomicity and stale-expect refusal.
- `docs/PLAN.md` row 12 is Done.

## Spec questions, with proposed answers

1. **SQLite persistence.** Spec says the stack also lives in the app's SQLite store. Proposed: approve a SQLite crate (rusqlite) in the PRD table and persist `UndoEntry` rows with the repo id; on startup, reconcile `refs/invoke-git/undo/*` against the rows and delete orphans. Until then, undo refs are named by the per-session op id, so a leftover ref from an earlier session may be overwritten by a new snapshot with the same number, and orphans are not pruned.
2. **"Exact" index.** `git read-tree` of a saved tree reproduces the index entries and tree exactly (mode, blob, stage, path) but not the index file's checksum (stat data is not restored). Law 8 is tested on entries and tree, not on the file's id. Proposed: define "index" in law 8 as entries and tree.
3. **Index check at undo time.** The spec only requires refs to be unchanged. I also refuse when the index id differs from what the operation left, because `read-tree` would overwrite staging done since. Risk: another tool that rewrites the index (even `git status`) makes undo refuse spuriously. Proposed: later compare the tree (written from a copy) instead of the file id.
4. **Re-basing after undo.** After an undo the index id changes, so without re-basing, a second undo would always refuse. The new top entry's expected index id is set from the next fresh read. Proposed: keep.
5. **Head and phase checks.** Undo also refuses when `HEAD` now names another branch (or is detached) and during a merge/rebase/cherry-pick/revert. Not in the spec; both protect other work. Proposed: add to the spec.
6. **Snapshot failure contract.** `SnapshotForUndo` and the operation's `RunGit` are emitted together, so the driver must skip `RunGit` when `snapshot` returns `Failed` (the test `Driver` does).

## Anything surprising

- `git write-tree` on the real index rewrites it (cache-tree extension), changing the index checksum. The snapshot therefore works on a private copy, and the test oracle does too.
- The tree saved for a commit equals the new commit's tree (a commit commits the index). It is still needed to restore the index after undo.
