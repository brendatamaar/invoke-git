# Task 021 handoff

Backlog task 21: Pre-push review screen. Branch `task-021-review`, stacked on `task-017-sync-ui`. Row 21 in `docs/PLAN.md` is "Done (UI checklist pending)".

## What changed

- **`shell::outgoing` (new).** `read_outgoing(paths, upstream)` gives the commits on `HEAD` that the upstream lacks (newest first by commit time, at most 1000, with a `truncated` flag), the base of the combined diff and the files that differ between base and `HEAD`. With an upstream the base is the merge base (`git diff @{u}...HEAD`), so a change that only arrived on the remote is not shown as ours. Without an upstream, or when it no longer exists, the commits are those no remote-tracking branch contains, and the base is the parent of the oldest one (the fork point for a branch cut from the remote's branch; the empty tree for a repository with no remote). `read_range_sides` gives the two sides of a file for the combined diff; per-commit sides are task 19's.
- **`shell::commit_detail`.** The file-list part of `read_commit` is now `changed_files(repo, old_tree, new_tree)`, shared with the combined diff; `tree_of` and `side` are `pub(crate)`. No behaviour change.
- **`app::review` (pure).** The title (`Review 2 commits before pushing`), the subtitle (`main → origin/main · fast-forward`, or `the remote has 1 new commit; fetch and rebase first`, or `new branch on the remote`), the button words (`Push 2 commits`, `Publish 1 commit`), the viewed ticks (a tick belongs to the diff it was made in: the combined one or one commit's) and the key (head and upstream tip) that says when the list is stale.
- **`app::review_view`.** The screen of the mockup: a header with the title, the subtitle and the `Combined` / `Per commit` switch; on the left the outgoing commits (click one to see it alone) and its files with a checkbox, a letter, and `+n −n`; the diff of the chosen file on the right (the task 10 viewer, read-only); a footer with `n of m files viewed`, `Back to changes` and the Push button. Reading, line counts and diffs run on background threads; an answer for a list or file that is no longer the chosen one is dropped.
- **Header.** `Push ↑N` is now `Review and push ↑N` (`Review and publish` for a branch without an upstream) and opens the review. Push itself is sent from the review; the strip under the header shows it going, and a rejected push brings back the choices of task 17 while the review reads the new outgoing set (the PRD's push flow, step 3). The sidebar is hidden while the review is open; `Changes` and `History` in the header leave it.
- **Cargo.** `shell` enables the `revision` feature of `gix` (needed for the merge base); `Cargo.lock` gains `gix-revision` and what it pulls in. It is a feature of a dependency already in the table, not a new dependency; say if it should be a separate commit.
- **Tests:** `shell` integration `outgoing` 9 (a property test against git, merges, a remote that moved, no upstream, a gone upstream, no remote, the limit via `fast-import`), `app` +7 (`review`).
- **Planted bugs, all caught:** the upstream ignored (nothing hidden), the base taken as the upstream tip instead of the merge base, oldest first, the cap off by one, no-upstream base as the empty tree, no-upstream hiding nothing, a tick that never unticks, the key ignoring the upstream tip, `1 commits`, `Publish` never used, `fast-forward` with one commit behind, a tick shared by every diff. One planted sort order first survived (the walk already gave newest first for a straight line); a merge test was added and then caught it.
- **I ran it on this laptop** (fresh data folder, local bare remote with two local commits): `Review and push ↑2` opened the review with both commits, three files with `+1 −0`, `+4 −1`, `+2 −1`, and the first file's diff; `Per commit` showed the newest commit's `notes.txt` diff with `+2 −1`; ticking a file showed `1 OF 2 VIEWED` and `1 of 2 files viewed`; `Push 2 commits` put both commits on the remote (checked with `git log` on the bare repo), and the review then read `Nothing to push` with `Back to changes`. Also seen while doing task 17: the page no longer runs past the window when the header is wide.
- Not run by me: a branch without an upstream (`Review and publish`), a remote that moved (`fast-forward` replaced by the warning), more than 1000 commits, binary or very large files in the list, a repository with no remote, 150% and 200% scale.

## What is unfinished

- **Notes and the to-do warning** of the mockup (task 22). The footer has room for the warning; there is no notes column.
- **Counts for big lists.** Line counts are worked out for the first 300 files; the others show none. Each count diffs the whole file once more than the viewer does; if that is slow on large pushes, move it into the shell.
- **Viewed ticks are not kept** when the screen is left or the list is read again (a fetch, a push); they belong to the open review.
- **No `n/m` keyboard stepping** (next unviewed file) and no select-all for the ticks.
- **Merge commits** are shown against their first parent only, as in the history (`merge` is written beside them).
- **A branch without an upstream** compares with every remote-tracking branch; with several remotes that is "what none of them has", which can be fewer commits than a push to one remote would send.

## Questions and proposed answers

1. **Does Push need the review every time?** Proposed (done): the header button opens it; there is no setting to skip. A "push without review" shortcut can come with a preference later.
2. **Where does the review live?** A page of the repo tab (not a tab of its own), so the header, the strip and the lock banner stay. The mockup's back arrow is the `Back to changes` button.

## Windows checklist (tasks 2, 7, 10, 11, 14, 15, 16, 17, 18, 19, 20 apply too)

1. In a repo with unpushed commits, the header says `Review and push ↑N`; press it: the review opens with `Review N commits before pushing` and `branch → origin/branch · fast-forward`.
2. The commits are listed newest first with their short hash and age; the files show a letter (`A`, `M`, `D`), a checkbox and `+n −n`. The first file's diff shows; click another file and its diff replaces it. Split and Unified, the context choices and the colours match the Changes page.
3. `Per commit`: the newest commit is chosen and its own files are listed; click another commit and the list and diff follow. Back on `Combined` the whole set is shown again.
4. Tick files: the label above the list and the footer count them (`1 OF 3 VIEWED`); a tick in one commit does not tick the same file in another or in the combined view.
5. Make the remote move (push from another clone) and press `Fetch` while the review is open: the list reads again and the subtitle says the remote has new commits; `Push` is then refused by the remote and the banner offers `Pull with rebase`. After it the review shows the new outgoing set.
6. `Push N commits`: the strip under the header shows the push; when it ends the review says `Nothing to push`.
7. A new branch with no upstream: the button says `Review and publish`, the subtitle says `new branch on the remote`, the footer button `Publish N commits`.
8. Branch with no commits ahead: the header `Push` is disabled; a detached HEAD: the review cannot be opened.
9. A commit that changes a binary file or a file over the size limit: the diff area explains why there is no text diff; the list still shows the file.
10. Long file names and commit subjects are cut with `…` and nothing runs past the window; 150% and 200% scale: the footer buttons are not clipped. `Changes` and `History` in the header leave the review.
