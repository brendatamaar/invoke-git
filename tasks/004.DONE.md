# Task 004 handoff

Backlog task 4: Shell: command runner, git CLI wrapper with progress and cancel.

## What changed

Branch `task-004-shell-runner`, from `main` at `22371da`.

- **New crate `crates/shell`** (package `shell`). It depends on `invoke-core` and `gix` (0.90, `sha1` only), plus `windows-sys` 0.61 on Windows only, which you approved on 2026-11-21. I added `windows-sys` to the PRD's build-vs-library table. `gix`, `proptest` and `windows-sys` are now workspace dependencies.
  - **`git.rs`:** `Git::detect(program)` runs `--version` and refuses git older than 2.40 with `SetupError::{Missing, Unparseable, TooOld}`. `parse_version` handles `2.45.1.windows.1`, `(Apple Git-146)` and `2.48.rc0`.
    - `invocation(&GitArgs)` builds argv as `-c core.quotepath=false -c color.ui=false <subcommand>`.
    - A commit is `commit --file=-`, plus `--amend` if asked. The message goes on stdin, so it never reaches argv: no Windows quoting or length limits, and no message can be read as an option.
    - Every run adds `GIT_TERMINAL_PROMPT=0` and `LANGUAGE=en` (see Q2). On Windows, every spawn uses `CREATE_NO_WINDOW`.
  - **`progress.rs`:** `Lines` splits stderr chunks on `\r` or `\n`. `parse` reads `Label: NN% (a/b)`, `Label: N, done.` and the same with a `remote: ` prefix. Labels must start with a capital letter, which keeps out `fatal:`, `error:` and `hint:` lines.
  - **`classify.rs`:** the one place a finished git becomes `OpOutcome`. Markers are checked in order: precondition (lock), then auth, network and expected outcomes. Anything else is `Bug`. The details keep the raw output.
  - **`precondition.rs`:** `RepoPaths { workdir, git_dir }`.
    - `current(paths)` reads `HEAD` through gix (opened with `Options::isolated()`). The index id is read straight from the index file's checksum trailer.
    - `check(paths, expect)` refuses with `PreconditionChanged` if `index.lock` exists, or if head or index differ from what the core expected.
  - **`tree.rs`:** each git child gets its own process tree.
    - **Windows:** a job object, terminated on cancel. It is not kill-on-close, so a daemon git starts on purpose (fsmonitor) survives a normal exit. `BREAKAWAY_OK` is set, so children that ask to leave can. If the job can't be created, cancel falls back to killing git alone.
    - **Unix:** a process group. Cancel sends SIGTERM to the group, so git can clean up its locks, then SIGKILL after 2 s. The group is only signalled while git is still unreaped, so its id can't have been reused.
  - **`runner.rs`:** `GitRunner::new(git, paths)`, with an optional `with_env(...)` (tests use it to isolate config).
    - `run(op, args, expect, Sender<Event>)` starts one thread per operation. It checks cancel and the preconditions first, then spawns git. Stdin is written on its own thread. Stdout and stderr are drained on their own threads, which keep the last 64 KiB of each, and stderr progress lines become `OpProgress`. It then polls for exit or cancel every 20 ms.
    - Each op ends with **exactly one** `OpFinished`. If a cancel loses the race to a git that already succeeded, the real outcome is reported.
    - After git exits, the output pipes get 500 ms to close, so a daemon still holding them can't hang the op.
    - `cancel(op)` sets a flag. Unknown or finished ops are ignored.
- **Tests:** 10 unit and property tests, and 9 integration tests on temp repos with system and global config shut out.
  - Property tests: chunking never changes the lines, formatted progress parses back, the progress parser never panics, and messages never reach argv.
  - Integration tests:
    - system git ≥ 2.40, and a missing git is reported
    - a commit moves HEAD with the exact message
    - a stale head (only the branch moved) is refused
    - a stale index is refused
    - a held `index.lock` is refused by the shell's own check, with the lock untouched

    - cancel right after start reports `Cancelled`
    - cancel of an unknown op is a no-op

## What is unfinished

- Nothing in scope. The other shell commands come with their tasks: `ReadState` (5), `ApplyPatchToIndex` (11), `SnapshotForUndo` (12), `AnswerAuth` and askpass (16), network argv and `--progress` (17). Wiring the runner to the app comes with task 7.

**Spec questions (proposed answers):**

1. **Stale lock files after a hard kill.** An experiment on git 2.43 showed that a plain `git commit` does not hold `index.lock` while the pre-commit hook runs, so killing it there leaves the repo unchanged. Other operations do hold locks while they work: `commit -a`, rebase steps, and ref updates (`refs/**.lock`). On Windows, terminating the job is a hard kill, and git can't remove its lock files. A leftover `index.lock` then looks like "another git process is running" forever. Deleting it automatically is unsafe, because the shell can't prove the lock is ours. **Proposed:** after a cancel, the core asks the user before removing a `*.lock` that the cancelled op could have created, and only if it is not newer than the kill. Do this together with law 13's owning "cancel at random points" test, which needs tasks 17 and 23.
2. **`LANGUAGE=en`.** The spec says to inherit the environment untouched, but classification has to match git's English messages. `LANGUAGE=en` changes the message language only; git has no `en` catalogue, so it prints its built-in English. **Proposed:** keep it, and note it in core-design's shell section next to `GIT_TERMINAL_PROMPT=0`.
3. **Unclassified failures are `Bug`.** A failing commit hook prints whatever it likes, so it lands in `Bug` ("error card with a copyable report"), and that is the wrong tone for a hook rejection. **Proposed:** add an error class such as `Rejected` for "git ran fine but refused, with its own message". The UI shows the output inline. Decide this in task 14, when the commit flow exists.
4. **Index id and `index.skipHash`.** When `index.skipHash=true` (an opt-in setting), git writes an all-zero checksum, so the index id never changes and the stale-index check can't see changes. **Proposed:** in task 5, when the trailer is all zeros, use the file's size and mtime as the id instead. Task 5 should reuse `precondition::index_id`, so the core's snapshot and the shell's check always agree.
5. **Job assignment race (Windows).** git runs for a moment before it is assigned to its job. A child git started in that moment would escape the job. git does its own setup before it starts any children, so this is unlikely. **Proposed:** accept it. Starting git suspended would need the main thread's handle, which `std` doesn't expose. That would need more Win32 code (`CreateProcessW` ourselves), which isn't worth it now.
6. **Unix process groups use the system `kill` binary**, not `libc`, which isn't in the build-vs-library table. macOS and Linux only run tests for now, so this is fine. **Proposed:** revisit only if macOS or Linux builds come back.

## Anything surprising

- **A planted bug was masked.** The first stale-head test also restaged a file, so the index check refused the write and hid a missing head check. The test now moves only the branch ref (`commit-tree` + `update-ref`) and asserts that the index id is unchanged.
- **Git's own lock refusal hid a missing check too.** With the shell's lock check removed, git's own refusal still made the held-lock test pass. The test now asserts that the shell's own check refused the write.
- **Windows cross-check works on the VPS.** gix with `sha1` only has no C build scripts, so `cargo check --target x86_64-pc-windows-msvc` works there without a Windows linker. That's a cheap way to type-check Windows-only code before pushing.
