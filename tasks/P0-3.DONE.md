# Task P0-3 handoff

Phase 0 task P0-3: Prototype B, the commit graph in `spike-graph`.

## What changed

Branch `p0-3-commit-graph`, based on `p0-2-diff-view` (P0-1 and P0-2 are not merged yet).

- **New dependency:** `gix` 0.90 with `default-features = false` and the features `sha1` and `max-performance`. The PRD lists gix for reads.
- **`walk.rs`:** a background thread opens the repo, walks from HEAD with `gix::traverse::commit::topo` (`Sorting::TopoOrder`, using the commit-graph file), lays out commits as it goes, and sends pages of 5,000 rows to the UI over a channel. `--limit` stops the walk (default 200,000).
- **`layout.rs`:** naive lane assignment, following spec steps 1–6, with colours rotating through 8 lanes.
  - Only edges that touch a commit's dot are stored, as `In` and `Out` edges.
  - Lanes that pass straight through a row are rebuilt for visible rows, from a lane snapshot taken every 128 rows (`lanes_at`, `apply`, `passing`). See "Anything surprising" for why.
- **`meta.rs`:** reads subject (first line), author name and date (`YYYY-MM-DD` UTC, no date crate) per commit.
  - A background reader runs 1,000 rows ahead of and behind the visible rows.
  - The UI thread reads only visible rows the prefetch has not reached yet, such as after a scrollbar jump. So rows are never painted without their data.
- **`view.rs`:**
  - 28 px rows in a `uniform_list`, with columns graph, subject, author, date and short hash.
  - The graph column is a `canvas` per row that draws straight lanes (`paint_quad`), curves for lane changes (`PathBuilder`) and the dot: filled for normal commits, hollow for merges, an `accent` ring for HEAD.
  - The graph column is sized to the widest visible row, capped at 16 lanes, with "+N" before the subject when a row has more.
  - It reuses the custom scrollbar, readout and stats from Prototype A.
  - `--sweep N` scrolls from the newest commit to 100,000 deep in N seconds, prints the stats and quits.
- **Tests (10):**
  - Linear history, branch and merge, octopus, two tips sharing a parent, colour rotation.
  - A generated 2,000-commit DAG checked for connectivity: every `In` edge has an open lane above it, passing lanes continue below, checkpoint replay equals a straight replay, and all lanes close at the roots.
  - Paged layout equals whole layout.
  - Date formatting.

  Each test failed under at least one of six mutations: not closing `In` lanes in `apply`, not freeing merged lanes, an off-by-one checkpoint, counting entering lanes as passing, a 7-colour rotation, and a wrong month.
- `cargo xtask check` passes. Clippy wanted `is_multiple_of`, now used.
- `docs/spike-results.md`: Prototype B results, the AC-power rerun of Prototype A, and new risk notes.

**Preliminary results** (plugged in, 60 Hz, no human input):
- Walk and layout: 200k commits in 0.7 s; first page in 76–78 ms.
- First paint: 27–45 ms after the first page.
- Fast 20 s sweep (100k deep) and slow 60 s sweep: 60.0 fps in every window, build p95 3.5–5.5 ms, worst frame 21–25 ms, 0 blank rows.
- Peak memory: 396 MB.

## What is unfinished

- **Not seen by me:** how the lanes, curves and dots look, the text columns, wheel feel and scrollbar drag. The checklist below covers them.
- **The cold-cache fast sweep with prefetch was not re-run.** The 183 ms frames came from a cold disk cache; by the time the prefetch existed, the cache was warm. A reboot (or another large repo) before P0-4 would test the cold case.
- **Out of scope for the spike:** ref labels, lane hover, selection, refs other than HEAD, refresh, shallow stubs and the missing-commit-graph banner.

**Spec gaps and questions:**

1. **The spec's row record can't store passing lanes.** `commit-graph.md` → "Row record" budgets about 16 bytes per row plus "an offset into a shared edge arena", and 1M commits under 100 MB. On the kernel the naive layout keeps up to 691 lanes open at once. Storing every lane that passes through each row cost 70.7 M edges and 773 MB for 200k commits. **Proposed answer:** amend the spec to store only the edges touching each dot, and rebuild passing lanes for visible rows from periodic lane snapshots, as the spike now does (431 k edges for 200k rows). Law 14's page-join property still holds; the spike tests it.
2. **Metadata reads belong off the UI thread.** The spec says metadata is read lazily for visible rows plus a buffer, but not on which thread. Reading on the UI thread caused frames up to 183 ms with a cold cache. **Proposed answer:** make the background reader explicit in the spec, with a synchronous fallback only for visible rows after a jump. This fits "IO only in `shell`".
3. **The P0-2 frame-metric question is mostly answered.** P0-2's question 2 asked whether PresentMon is needed, because the in-app frame-interval p95 read 22–25 ms at idle. **That jitter was caused by battery power.** On AC, interval p95 is 17.3–18.0 ms during sweeps, build p95 is 3.5–5.5 ms, and the worst frames are 20–25 ms. **Proposed answer:** gate with the in-app readouts, always plugged in. "p95 ≤ 16.7 ms" should read as "60 fps with p95 frame interval within one vsync plus jitter (≤ 18 ms) and no frame over 50 ms". PresentMon becomes optional and needs no install unless a result is borderline.
4. **The naive layout makes the kernel graph very wide.** 691 open lanes at the widest point means most of the graph is beyond the 16-lane cap (the "+N" marker). That is the naive layout working as specified on a huge topology. **Proposed answer:** accept it for Phase 0. Lane compaction is a v0.1 graph-task decision (backlog task 18), not a spike blocker.

## Anything surprising

- **The kernel's topological order holds hundreds of lanes open.** I expected a few dozen. This drove the change to store only the edges that touch a dot.
- **Battery power distorted the P0-2 measurements.** The same diff sweep on AC dropped build p95 from 16.4–18.6 ms to 4.7–4.9 ms, frame-interval p95 from 21–23 ms to 17.8 ms, and first paint from 79–115 ms to 39 ms. The battery numbers in `docs/spike-results.md` are now marked as such.
- **gix 0.90's topo walker is fast.** 200k commits from the commit-graph file in 0.7 s, including layout.
- **The first walk after a reboot is slow.** The very first run took 737 ms for the first page (cold), against 76–78 ms afterwards.
- Custom drawing in GPUI (`canvas`, `paint_quad`, `PathBuilder::stroke` with `curve_to`) needed no workarounds.

## Windows checklist for UI changes

Plug the laptop in and close heavy apps. From the repo root in PowerShell:

1. `git switch p0-3-commit-graph`
2. `cargo run --release -p spike-graph` (reads `C:\dev\fixtures\linux`; pass another repo path to change it)
   - [ ] A window titled **spike-graph** opens. Within a second the header shows the repo path, `200000 commits` (or a count still rising), and the readout.
   - [ ] Rows are 28 px tall: a graph column, then subject (white), author and date (grey), and an 8-character hash (monospace, faint).
   - [ ] The first row's dot is an indigo ring (HEAD). Merge commits have hollow dots; others are filled in their lane colour.
   - [ ] Lanes are coloured vertical lines, 14 px apart. Branches leave and join with smooth quarter curves; each lane keeps one colour from top to bottom.
   - [ ] Where more than 16 lanes are open, a faint `+N` appears before the subject.
   - [ ] The console prints the walk start, `first page … ready`, `first paint …`, `walk done …`, and a stats line every 5 s.
3. Wheel scrolling:
   - [ ] Scroll quickly for 10 s. Subjects, authors and dates are always filled in (no empty rows), and the readout's `blank` stays 0.
   - [ ] Lane lines join cleanly between rows (no gaps or offsets at row edges).
4. Scrollbar:
   - [ ] Drag the thumb from top to bottom three times. Rows follow the pointer down to commit 200,000 and back, with text present immediately after each drag stops.
   - [ ] Clicking the empty track jumps there.
5. Automated sweep: run `cargo run --release -p spike-graph -- --sweep 20`.
   - [ ] It scrolls 100,000 commits deep in about 20 s, then quits and prints `sweep done …`. Send me the console output.
6. Task Manager:
   - [ ] Peak memory is around 250–400 MB.
