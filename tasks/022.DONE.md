# Task 022 handoff

Backlog task 22: Notes and annotations (SQLite store), to-do warning on push. Branch `task-022-notes`, stacked on `task-023-conflicts-ui`. Row 22 in `docs/PLAN.md` is "Done (UI checklist pending)". Part 1 is the notes (the first commit of the branch), part 2 is the undo stack kept in the same file (the second one, described under "Part 2" at the end).

## What changed

- **`rusqlite` is added** (approved 2026-11-22), version 0.37 with `bundled` (SQLite built from source, nothing to install), in the workspace table and used only by `shell`. `Cargo.lock` gains it and its few helpers (`libsqlite3-sys`, `hashlink`, ...).
- **`invoke_core::notes` (pure).** `Note`, `Anchor { commit, path, line, text }` (the line is on the new side of the diff, and its text is kept), `clean_body` (trimmed, line endings as `\n`, not empty, at most 4000 characters), `line_of`, `open_todos`, and `relocate(anchor, text)`: where the anchored line is now (the same number if it still holds the same text, else the nearest line that does, else none).
- **`shell::store`.** One file, `notes.sqlite` in the app data folder (`%APPDATA%\Invoke Git`, or `INVOKE_GIT_DATA_DIR`), schema version in `PRAGMA user_version` (a newer file is refused, not guessed at), parameters only (no text is ever put into SQL), every row names its repo and every change is scoped to it. Add, list (by file, line, age), resolve and reopen, edit, delete, and `reanchor`. The clock is the caller's.
- **`app::notes_db`.** The store as the screens use it: one per run, opened on first use, the repo key (the folder spelled one way whatever way it was opened) and the time. Every call does file IO and runs on a background thread.
- **The review screen.** A `NOTES · n` section on the left (a `TO-DO` or `RESOLVED` tag, `path:line`, the text, `Resolve` or `Reopen`, `Delete`; clicking a note opens its file); a form under the diff (`Line`, the note, `To-do`, `Add note`) that adds a note on that line of the file on show, counted on the new side; and `⚠ 1 to-do note is unresolved` beside the Push button while to-dos are open (it does not block the push). A bad line number or an empty note says so and saves nothing.
- **Surviving a rebase.** A note is written on the commit on screen (one outgoing commit, or the tip for the combined diff). When the review opens and a note of the same branch is on a commit that is no longer in the push, but its file is still changed by it, the shell reads the file's new side and moves the note to the tip at the line where its text is now. A note whose line is gone stays where it was and is not shown.
- **Tests:** `core` +7 (`notes`), `shell` lib +7 (`store`), `app` +4 (`review` additions) +3 (`notes_db`).
- **Planted bugs, all caught:** equal distances picking the later line, resolved to-dos still counted, a body not trimmed, line 0 accepted, resolve ignoring the repo, notes not ordered, a newer file accepted (first planted so that it failed to compile; replanted to compile, then caught), editing a plain note keeping `resolved`, re-anchoring ignoring the repo, any branch adopted, tip notes not belonging to the review, the plural of the warning.
- **I ran it on this laptop** (fresh data folder, local bare remote): in the review, line `4` and the text `Check this call twice` with `To-do` ticked and `Add note` gave a `TO-DO main.rs:4` note and `⚠ 1 to-do note is unresolved` in the footer; after closing the app and amending the tip commit (new id), reopening the review showed the same note on `main.rs:4`, and `Resolve` changed it to `RESOLVED` and removed the warning.
- Not run by me: a note in per-commit mode, a note on a line that moves (inserted lines above), a note whose line is gone, `Delete`, two repos with notes, a note with a very long text, 150% and 200% scale.

## What is unfinished

- **Notes are not drawn in the diff** (the mockup shows a card under the line); they are listed beside it and chosen by line number. Proposed: a gutter button per line in `DiffView` that fills the form.
- **A note's text cannot be edited** (only resolved, reopened or deleted). The store has `edit_note`; the screen has no button yet.
- **Notes only in the review.** The Changes and History pages have no notes.
- **Identity of a repo** is its folder (spelled one way). Moving the folder loses its notes. Proposed: key by the root commit when the history is cheap to read.
- **Line counts and note anchors** use the text of the new side; a note on a removed line (old side) cannot be written.

## Questions and proposed answers

1. **Is a to-do warning a block?** Proposed (done): no, only a warning; the user pushes anyway.
2. **Branch in a note.** Added so that a rewritten note is only moved on the branch it was written for (otherwise a stale note of an old branch could land on any push that touches the same file with a line of the same text).

## Windows checklist (tasks 2, 7, 10, 11, 14, 15, 16, 17, 18, 19, 20, 21, 23 apply too)

1. Open the review of a branch with commits ahead. Under the diff there is `Add a note on <file>`. Type a line number (a line of the new side), some text, tick `To-do` and press `Add note`: a `TO-DO <file>:<line>` entry shows under `NOTES`, and the footer says `⚠ 1 to-do note is unresolved`.
2. A line number of 0, a letter, or one past the end of the file: a message says what is wrong and nothing is saved. An empty note: the same.
3. Close the app and open it again; open the review: the note is still there (the database is `%APPDATA%\Invoke Git\notes.sqlite`).
4. `Resolve`: the tag becomes `RESOLVED`, the footer warning goes; `Reopen` brings both back. A note without `To-do` has no Resolve button and no warning. `Delete` removes it.
5. Click a note: its file opens in the combined diff.
6. Rewrite a commit of the branch (reword it, or rebase) and open the review again: the note is still listed on the same line (it moved with its text). Change the line's text in the rewrite: the note is no longer shown.
7. Two repos with notes each show only their own.
8. In per-commit mode, add a note: it is listed in the same place; the warning counts it.
9. Long note texts wrap and the list scrolls; nothing runs past the window at 150% and 200% scale.

## Part 2: the undo stack survives a restart (the task 12 follow-up)

Branch `task-022-notes`, second commit.

### What changed

- **`invoke_core::undo_codec` (pure).** One undo entry as one line of text and back: a version word (`u1`), then tab-separated fields, text fields escaped, counts before the lists they count. A line that is not exactly what `encode` writes (a cut, an unknown word, a second spelling of a number, fields left over) is an error, never a guess. Property tests: every entry round-trips (all five kinds of reversal, all reasons, any text), an accepted line encodes back to itself, a cut line is refused, and no text panics.
- **`Event::UndoStackRestored(entries)`**, handled by `UndoStack::restore`: the entries are taken only while the stack is empty and no operation is in flight (anything recorded in this run is newer and wins); only the newest 50 are kept, the older ones are named in a `PruneUndo`; and `ops.next` moves past the highest restored op id. Op ids name the saved trees (`refs/invoke-git/undo/<op>`), so a new operation reusing a restored id would overwrite another point's tree.
- **`shell::store` version 2.** The schema now goes from version to version in steps that only add: version 2 adds the `undo` table (repo, position, one line per point). A file from the first build gains it and keeps its notes (a test builds a version 1 file by hand). `save_undo` replaces a repo's points as a whole in one transaction; `load_undo` returns them in order and counts the rows it could not read (skipped, not guessed).
- **`shell::undo::reconcile`.** Checks the points of the last run against the refs now in the repo: a point whose saved tree (and stash copy, or both discard copies) is gone is left out; the refs of ops that have none of their own (a point that fell off, a crash between a snapshot and its record) are returned for pruning. The op of a ref is read from its name (`12`, `12-stash`, `12-discard`, `12-discard-after`).
- **`app::session`.** When a repo opens, a background thread loads the stored points, reconciles them, prunes the stale refs and sends the kept points to the core. **No snapshot is taken before that is done** (a gate), so a new operation's tree cannot be taken for a stale one and deleted. After every step, if the stack differs from what was last written, it is written again, off the UI thread; saves carry a number so an older save that finishes late cannot overwrite a newer one (`NotesDb::save_undo`).
- **Spec:** `docs/spec/core-design.md` ("the stack keeps the last 50 points ...") now says how it works.
- **Tests:** `core` +6 (`undo_codec`) +5 (`undo_restore`), `shell` lib +3 (store) +2 (`reconcile`), `shell` integration +2 (`undo_reconcile`, real git), `app` +1 (`notes_db`).
- **Planted bugs, all caught:** a tab not escaped, leftover fields accepted, a stash-kept point read as a stash-store one, one reason read as another, a restore over a live stack, the oldest points kept instead of the newest, op ids not moved past the restored ones, a save that keeps the old rows, points not read in order (the first test used ids whose text order equals their number order; changed), unreadable rows not counted, the discard point not needing its after copy, the orphan list inverted, the saved tree not required, and a save with the same number as the last one overwriting.
- **I ran it on this laptop** (fresh data folder): committed from the app (`Commit 'undo me please'` appeared beside `Undo`), closed the app and opened it again: `Undo` and its label were still there; pressing it put the repo back (`git log` at the base commit, both files staged again) and left no `refs/invoke-git/undo/*` ref.
- Not run by me: a restart after a stash drop, a discard, or a branch rename (they use the stash and discard copies), a restart after the repo was changed by hand (undo should refuse: the checks are the core's and unchanged), a restart with the store file locked, two Invoke Git processes on one store.

### What is unfinished

- **A failed save is silent.** The stack is then in memory only, as before; no banner. Proposed: a one-line notice once per run.
- **Two processes** on one store are serialised by SQLite's own lock (a two-second wait); the last writer's stack wins. Proposed: nothing, until there is a reason to run two.
- **A point taken off the stack for an undo in flight** is not in the store until the undo ends; a crash in that window loses that one point (its refs are cleaned at the next start).
- **Op numbering** restarts at 1 for a repo with nothing restored; stale refs of old runs are pruned at start, so this is safe, but ids in the refs are not unique over time. Proposed: keep it; nothing reads an id across runs.

### Part 2 checklist (add to the one above)

1. Make a commit in the app (stage a file, write a message, Commit): the header shows `Undo` and `Commit '...'`. Close the app and open it again on the same repo: `Undo` and the label are still there. Press `Undo`: the commit is gone, the files are staged again.
2. Do the same with a branch rename or delete, a stash drop and a discard of a few lines: each comes back as an undo after a restart.
3. After a restart, change the repo in a terminal (commit something) and press `Undo`: it refuses and says what moved; nothing is touched.
4. `git for-each-ref refs/invoke-git` after an undo and after closing: only the refs of points still on the stack remain.
5. Delete `%APPDATA%\Invoke Git\notes.sqlite` while the app is closed: the app starts, with no undo and no notes, and creates the file again. Notes and undo points live in the same file.
