## What is unfinished

- Nothing in scope beyond the visual check below.
- **Question: does `cargo xtask check` exist yet?** The task said no, but it was added in `57f072f`. It runs and passes. I ran both it and the three explicit commands. **Proposed answer:** use `cargo xtask check` from now on.
- **Question: is "release builds only" at odds with `cargo test` and clippy?** Both build GPUI in the debug profile, which costs 2.2 GB of `target/debug` and about 4 minutes on a cold cache. The explicit check commands require it, so I ran them. **Proposed answer:** accept the debug cost. Running `cargo clean --profile dev` after checks would reclaim it, but the next check would then rebuild cold.
- **Question: is the fixture generator allowed in `xtask`?** The task said "a fixture script". I made it an xtask subcommand instead of a shell or Python script, because it then needs no interpreter and no new dependency, works the same on Windows and the VPS, and never builds GPUI. **Proposed answer:** keep it.
- **Question: where do the spike crates live?** Under `crates/`, matching the paths in the design mockups (`crates/diff/...`). `xtask/` stays at the root. **Proposed answer:** put future product crates under `crates/` too.

## Anything surprising

- **Zed versioning changed.** Tags jumped from `v0.233.x` (April 2026) to `v1.x`. Sorting `v0.*` tags alone gives a seven-month-old release. Look at `v1.*`.
- **`[patch]` does not travel.** Zed's workspace patches `async-task` to its fork, and GPUI depends on that fork. Our workspace must repeat the patch. It built first try with only that one patch. The other Zed patches (calloop, notify, livekit, …) are not on GPUI's Windows path.
- **`gpui_platform` is required.** At this revision `gpui` alone has no platform backend; `gpui_platform::application()` creates the app. Its Windows backend needs no features.
- **The kernel checkout breaks on case-insensitive NTFS.** 13 files show as modified straight after the clone, because the kernel has paths that differ only by case. The graph spike is unaffected, but it is a real Windows case for the status view later (AGENTS.md lists case-insensitive paths as a Windows concern).
- **A blobless clone still downloads blobs for the checkout.** The working-tree checkout fetched blobs for HEAD. `--no-checkout` would have saved that time and disk, since the spike reads only commits.
- **Cargo 1.100's build-dir layout** puts test executables under `target\debug\build\<pkg>\<hash>\out\`, not `target\debug\deps\`. Scripts that look for test binaries should not hard-code the old path.
- Zed itself pins Rust 1.98.1 at this tag; 1.100.0 built it without warnings.

## Windows checklist for UI changes

From the repo root in PowerShell, with nothing else heavy running:

1. `git switch p0-1-spike-scaffold`
2. `cargo run --release -p spike-diff`
   - [ ] A window titled **spike-diff** opens, about 1200×800, centred on screen.
   - [ ] The whole window is a near-black background (`#0e0f11`).
   - [ ] The text **spike-diff** is centred, in grey (`#8a8f98`), and the glyphs are crisp (DirectWrite text works).
   - [ ] Resizing and maximising repaint with no white or garbage flashes.
   - [ ] Closing the window ends the process and returns the prompt.
3. `cargo run --release -p spike-graph`
   - [ ] The same checks, with the title and label **spike-graph**.
4. `cargo xtask fixtures`
   - [ ] It prints that it wrote `old.rs` (50000 lines) and `new.rs` (50104 lines), and "2000 changed".
   - [ ] `git status` does not list `fixtures/`.
5. Optional: with a window open, check Task Manager. Expect about 85 MB of memory, and GPU use near 0% at idle.

If a window does not open or closes at once, run it from a terminal and send me the console output.
