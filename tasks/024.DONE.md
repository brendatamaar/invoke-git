2. **Model-based harness** (`src/{app,world,transition,content,gitdir,observe,model}.rs`, `tests/model_based.rs`). `proptest-state-machine` generates sequences of up to 40 steps. The real `core::step()` plus the shell runners (git, staging, undo, state read) run each sequence on one temp repo (the "app"); plain git runs it on a twin. Both repos use fixed identity and dates, so the same commit has the same id in both. Actions: write, remove and rename files (CRLF, no final newline, unicode names and text); stage and unstage a file, hunk or line selection; stage every hunk (law 5); stage a selection then unstage the file (law 6); commit and amend; create (optionally switch), switch, rename, delete branch; stash save, apply, pop, drop; undo; refresh; outside `git commit -a`, outside `git checkout` (branch or detached); and any app write while another process holds `index.lock` (law 12: the harness checks that `.git` is byte-for-byte unchanged while the lock is held, then that the write runs after release).
   After every step it compares, app repo against twin: `HEAD`, every ref, index entries, stash reflog, and every worktree file. It also checks: the app's `RepoState` against a fresh `read_state` (and, after one more watcher event, with no tolerance), against `git for-each-ref` and `git status` (law 11); that the saved undo trees under `refs/invoke-git/undo/` are exactly those of the undo stack; that the undo stack matches a model built from the twin; that nothing is left in `.git` (`index.lock`, `invoke-undo-index-*`); and that every refusal has a typed reason and every failure is class `Expected`. Law 4 is checked per stage and unstage request, law 5 after stage-every-hunk (index blob equals worktree bytes), law 6 after stage-then-unstage (index entry for the path as before).
   **The twin's undo** is the spec's: the twin saves its refs and index tree before each step and restores them with plain git (`update-ref`, `symbolic-ref` or `switch`, `read-tree`, `stash store`). The model decides from the twin alone whether an undo must succeed, must be refused (empty stack, irreversible top, something moved) or either (an outside process touched the repo since, so the app may refuse on an index file that was only rewritten).
   **Shrinking and replay.** A failing sequence is shrunk by proptest (bounded to 600 iterations or 3 minutes) and the failure message ends with the twin's history as a bash script of plain git commands (file writes as `printf`, patches as heredocs). Example from the planted bug "undo forgets the index", shrunk to three steps:
   ```
   # --- step 1: WriteFile { file: 1, change: Whole { lines: [] ... } }
   mkdir -p "$(dirname dir/b.txt)" && printf %s $'' > dir/b.txt
   # --- step 2: Stage { file: 1, pick: File }
   T0=$(git write-tree)  # saved index
   git add -- dir/b.txt
   # --- step 3: Undo
   git read-tree "$T0"
   ```
   with "the index differs" and both indexes printed above it.

## Anything surprising (findings in the code under test)

1. **Any plain git command can make a later undo refuse.** An undo rebuilds the index with `git read-tree`, which leaves entries without stat data. The next ordinary git command (`git status`, `git diff`, a failed `git commit`, a no-op `git stash`) refreshes the index and rewrites the file with the same content and a new checksum. The app compares checksums, so the entry below the undone one now sees a "changed" index and the next undo is refused with `Changed(Index)`. Checked by hand: after `read-tree` the checksum is `931f...`; after `git status` it is `6e78...`. A user who undoes a stage and runs `git status` in a terminal hits this. A false refusal, not data loss. The harness treats an undo after any outside git process (or a failed git run) as "either" and requires only that a refusal is `Changed(_)`.
2. **Rename `topic` to `topic/x` is refused** (`NameConflict(topic)`) although git allows it (the old name goes away). `crates/core/src/branch.rs` `conflicting()` includes the branch being renamed. The harness does not generate nested rename pairs (`world.rs`, "Known gap").
3. **`git stash push` with nothing to save exits 0**; the app reports it as an expected failure (no entry pushed). Fine; the harness accepts a failed app op when git succeeded without changing anything.
4. **git quirk:** `git switch -c topic/x` while a branch `topic` exists checks files out and only then fails on the ref name, leaving the worktree on the new commit with HEAD unmoved. The app refuses first and changes nothing, which is better. The harness therefore asks git on a throwaway copy of the twin whenever the app refuses.
5. **Undoing a branch switch is a real checkout** and can fail when local changes are in the way; the app reports it as an expected failure and keeps the entry. The twin must refuse too, and does.
6. **The snapshot is stale after the app prunes old undo points.** The read that follows an operation lands before `PruneUndo` deletes `refs/invoke-git/undo/*`, so for a moment `snapshot.refs` lists refs that are gone, until the watcher's next event (real app) or the harness's. Harmless; the harness compares everything but those refs strictly and then everything after the next watcher event.
7. A conflicting `git stash pop` leaves unmerged index entries. The app cannot resolve them yet, so the harness resets both repos (`git reset --hard`) as an outside action and counts it (about 1 in 100 sequences).
8. The status read has no rename detection (task 11); the harness runs `git status --no-renames`.

## Spec questions, with proposed answers

1. **Undo refused after an index refresh (finding 1).** Proposed: keep the checksum as the cheap check, and when it differs compare the index by content: the shell can write a tree from a private copy of the index (as `SnapshotForUndo` already does) and the entry stores the tree id it left (`after_tree`); refuse only when the tree differs. That also lets the harness require acceptance after outside `git status`.
2. **Rename to a name nested with the old one (finding 2).** Proposed: exclude the branch being renamed from the `NameConflict` search in `branch::conflicting`. Then drop the exclusion in the harness.
3. **Quint: simulation, not model checking.** `quint run` (random simulation, no Java) is what CI runs. `quint verify` needs Java 17 and an Apalache download from GitHub releases and could not be tried on this VPS (no Java). Proposed: add a `quint verify` step with `actions/setup-java` once someone can try it; the specs are small enough to check exhaustively.
4. **Windows runs 32 sequences, not 256.** The harness starts several thousand git processes per 256 sequences, slow on Windows. Linux and macOS run the full 256 on every push and Linux runs 10,000 nightly. Proposed: keep 32 unless the first Windows run is fast; raise it by editing the env in `ci.yml`.
5. **A race that spec 1 cannot show.** The shell checks the expected index and head, then starts git; an outside write between the two is not caught by the check (git's own `index.lock` protects only the write itself). `refresh_vs_user.qnt` models check-and-run as one step and says so in a comment. Proposed: for `commit`, pass the expected head to git (`git commit` has no such flag; `update-ref` with the old value would) and for `apply --cached`, take `index.lock` ourselves around check and run. Out of scope here.
6. **One owner per law.** The verification doc wants exactly one owning test per law; for the model-based laws (4, 5, 6, 8, 9, 11) the owner is one test function, `model_based_sequences`, that checks all of them and finds each by a message marker. The registry would break if a check were dropped from the harness without removing its marker. Proposed: keep as is.
