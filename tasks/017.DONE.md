# Task 017 handoff

Backlog task 17: Fetch, pull (merge or rebase), push with `--force-with-lease`, set upstream. **Core half only.** The fetch/pull/push controls and the rejected-push prompt (UI) wait for the Phase 0 gate; row 17 in `docs/PLAN.md` is "Core done".

## What changed

Branch `task-017-sync-rebased`, rebased onto `origin/main` at `53e3cc0` (original `task-017-sync` was from `0dcfb0b`). Lease values come from `RefsSnapshot.refs`, the same snapshot task 15 fills (its `upstreams` map holds ahead/behind, not object ids, so there is no second source).

- **core `ops.rs`:** `WriteRequest` and `GitArgs` gain `Fetch`, `Pull`, `Push`, `SetUpstream`. New `RemoteBranch` (with `tracking_ref()` / `remote_ref()`), `PullMode`, and `Lease { remote_ref, expected }`. A force push is `Push { lease: Some(..) }`: there is no force flag, so a force without an expected value cannot be expressed (law 10). `GitArgs::is_network()`.
- **core `event.rs` / `step.rs`:** `PushRequested` now carries `{ to, force_with_lease, set_upstream }` (was `{ force_with_lease }`); new `FetchRequested`, `PullRequested`, `SetUpstreamRequested`. The branch and, for a force, the lease are taken from the snapshot **at request time** (the value the user reviewed); a fetch that moves the remote-tracking ref before the push runs makes the remote refuse (stale info) rather than overwrite. Refusals (new `Refusal` variants): `NotRead`, `NoBranch` (detached/unborn), `NoRemoteValue(ref)` (force without a known value), `BranchChanged` (checked at dispatch, since the request may have waited), plus `RepoBusy` for a pull during a merge/rebase. Fetch and set-upstream queue like any write; push and pull take an undo point. `Notice::PushRejected` replaces `OpEnded` when a push ends `Failed(Expected)`. `Action` gains `Fetch`, `Pull`, `SetUpstream`. An accepted request now clears a stale `Refused` notice.
- **undo (after rebasing onto tasks 11, 15, 20):** push and pull record their point with `reverse: Reversal::Never(Irreversible::Push | Irreversible::Pull)` (task 20's type; `Irreversible::Pull` is new), so settling and the undo refusal reuse the existing path. `WriteRequest::takes_undo_point()` is false for fetch and set-upstream. A push is `IndexEffect::Untouched`, a pull `Rewrites`.
- **shell `git.rs`:** argv for `fetch --progress -- <remote>`, `pull --progress (--no-rebase --no-edit | --rebase --no-autostash) -- <remote> refs/heads/<b>`, `push --progress [--force-with-lease=<ref>:<oid>] [--set-upstream] -- <remote> refs/heads/<l>:refs/heads/<b>` (no `+`), `branch --set-upstream-to=<remote>/<b> -- <local>`.
- **shell `runner.rs`:** `GitRunner::with_askpass(program)` and `answer(op, answer)` reuse task 16's `AskpassServer` for network ops, mapping prompts to `Event::AuthNeeded`. Cancel, progress and the precondition check are the existing ones.
- **shell `classify.rs`:** `[remote rejected]`, `stale info`, `couldn't find remote ref`, `cannot pull with rebase`, `would be overwritten by merge`, `Not possible to fast-forward` are `Expected`.
- **Tests:** shell lib +4 (argv unit, 3 proptests, one over all request shapes including option-looking names); core `step_props` +3 proptests and 7 unit tests; `crates/shell/tests/sync.rs` 14 integration tests (local bare remote); askpass e2e +2 (fetch and push against the 401 server).

## Questions and proposed answers

1. **Pull and undo.** The spec says undo never rewrites working-tree files, but a pull does. Proposed (implemented): pull leaves an irreversible marker. Alternative: no marker at all.
2. **Push marker needs a saved tree.** Push and pull call `SnapshotForUndo` only so the marker has a tree; wasteful but keeps the entry shape. Proposed: allow `UndoEntry.tree: Option<Oid>` later.
3. **`PushRejected` is derived from the request kind** (a push that ends `Expected`), so "remote does not exist" is also shown as rejected. Proposed: classify push stderr into a typed reason at the shell boundary when the UI needs the distinction.
4. **Lease at request time.** Chosen so the lease is what the user reviewed. If the UI keeps a review screen open across a fetch, it must re-issue the request.
5. `PushRequested` signature changed (needed to name the remote); callers in the UI half must adapt.

## Anything surprising

- `git push`/`pull`/`fetch` accept `--` before the remote, so remote and branch names that look like options are harmless; the proptest includes `-f`, `--force`, `+main`.
- The cancel test needs the slow hook only while a marker file exists, so fixture setup stays fast.
- The sandbox for this agent could not run compound shell commands, so scripts were written to files.

## UI half (added 2026-11-23, branch `task-017-sync-ui`)

Row 17 in `docs/PLAN.md` is now "Done (UI checklist pending)".

- **`app::sync` (pure).** From one snapshot it works out what the buttons ask for: the remote branch is the branch's upstream; a branch without one is published to `origin` (else the one remote we have refs of) under its own name and the push sets the upstream. `Pull` needs an upstream that exists and no merge or rebase in progress; `Push` needs commits ahead (or no upstream, or a gone one); a detached HEAD can only fetch. `Pull with rebase` appears only when the branch has diverged. Also the words for an operation in progress (`Fetching origin`, `Pushing to origin/main`, `Force pushing to ...`) and its progress.
- **`app::sync_view`.** `SyncButtons` (Fetch, Pull ↓N, Pull with rebase, Push ↑N / Publish branch) sit in the header of a repo tab and are disabled while an operation runs. `SyncStrip` under the header shows: a network operation with its stage, a bar and Cancel; the credential question (the task 16 `AuthPromptView`; answers go to `AuthAnswered`, Cancel cancels the operation); after a rejected push, `Fetch`, `Pull with rebase`, `Force push…` and `Dismiss`; and a leftover lock.
- **Force push.** `Force push…` asks first (the text says commits on the remote that you do not have are lost, and that it only works if nobody pushed since the last fetch). The core takes the lease from the remote-tracking value in the snapshot, so a remote that moved after the last fetch refuses it. After a Fetch the lease is the new value: the user has chosen to replace what they just fetched.
- **Credentials.** The session registers the `askpass` helper next to the exe for git runs (task 16's helper). If the helper is not there, network operations fail with git's own message rather than waiting for a console (`GIT_TERMINAL_PROMPT=0`).
- **Leftover lock (the stale-lock decision recorded in the core half).** New core event `RemoveStaleLockRequested` and `Command::RemoveStaleLock`: accepted only when the snapshot shows `index.lock` held by someone else and none of our operations is running or waiting; otherwise `Refusal::NoStaleLock`. The shell removes that one file (`shell::remove_index_lock`) and answers with `DiskChanged(Index)` so the state is read again. The UI shows "Another git process is running…" with `Remove lock file…`, then a second question before it deletes anything. The old plain lock banner in the header is gone (this strip replaces it). It is offered whenever the lock is someone else's, not only after a cancel: the core cannot tell a cancelled git from a crashed one, so the question carries the warning.
- **Layout fix found while running it.** A wide header (more controls) pushed the whole page past the window (the path did not shrink, the diff toolbar was clipped). The path now takes the leftover width and is cut with an ellipsis, and the repo view may shrink (`min_w(0)`).
- **Tests:** `app` +12 (`sync`), `core` step_props +2 (one proptest: a lock is removed only when it cannot be ours; one unit), `shell` lib +1.
- **Planted bugs, all caught:** `set_upstream` dropped on the first push, a pull allowed during a merge, the tracking ref split at the last slash, the lock offered while an operation runs, the core removing a lock while an operation is queued, the core removing a lock our own git holds, the shell removing `HEAD.lock` instead of `index.lock`.
- **I ran it on this laptop** (fresh data folder, local bare remote): `Fetch` moved `origin/main` and the header showed `↑1 ↓1`, with `Pull ↓1` and `Pull with rebase` shown; `Push` was rejected and the banner showed its four choices; `Force push…` showed the question; `Pull with rebase` left `↑1 ↓0`, and `Push` then put the commit on the remote (checked with `git log` on the bare repo). Against the 401 server: `Publish branch` showed `Git needs a user name` in the strip with the field focused, then the password step, then `Authentication failed.` with git's last line. With a planted `.git/index.lock`: the banner appeared, `Remove lock file…` asked again, `Remove lock file` deleted it and the banner went away.
- Not run by me: Cancel while a large fetch is moving, a pull that conflicts (the conflict screen is task 23), a first push to a remote that does not have the branch, SSH, more than one remote, a branch with a `/` in its name, 150% and 200% scale.

### What is unfinished

- **Pull mode is not a setting.** `Pull` merges (fast-forwards when it can); rebase is offered only when diverged or after a rejected push. Proposed: read `pull.rebase` from config later.
- **Remote choice.** A branch without an upstream goes to `origin`; with several remotes and no `origin` it takes the first one that has refs. There is no remote picker or `Set upstream…` for an existing branch (`SetUpstreamRequested` is wired in the core but has no button; the first push sets it).
- **The Push button goes straight to the push.** Task 21 puts the review screen in front of it.
- **A pull that conflicts** ends as an expected failure with git's words; the resolution screen is task 23.
- **Removing the lock can fail** (Windows keeps a file open): the state is read again and the banner stays; no error text yet.
- A remote name that contains a slash is split at the first slash (a branch name that contains one is handled).

### Windows checklist (tasks 2, 7, 10, 11, 14, 15, 16, 18, 19, 20 apply too)

Build the helper too: `cargo build --release --workspace`, then run `target\release\invoke-git.exe`.

1. Open a repo that has an `origin`: the header shows `Fetch`, `Pull`, `Push` after the tracking text. `Fetch` runs, a strip with a bar and `Cancel` shows for slow ones, and the `↑ ↓` counts in the header and sidebar update.
2. Push a branch that is ahead: the button says `Push ↑N`; afterwards `origin/<branch>` has the commits and the counts go to `↑0`.
3. Make a new local branch and press `Publish branch`: the branch appears on the remote and the header shows it tracking (`↑0 ↓0`).
4. Make the remote move (push from another clone), then `Push`: the yellow banner `Push rejected…` with `Fetch`, `Pull with rebase`, `Force push…`, `Dismiss`. `Fetch` then shows `↓1`; `Pull with rebase` brings the branch level; `Push` then works.
5. `Force push…` shows the question; `Cancel` closes it; `Force push` replaces the remote branch only when the remote is where you last fetched it (after another push from elsewhere without fetching, git refuses with `stale info`).
6. `Pull ↓N` fast-forwards a branch that is only behind. With both `↑` and `↓`, `Pull with rebase` appears; use it on a branch that rebases cleanly.
7. Detached HEAD: only `Fetch` is enabled. During a merge or rebase: `Pull` is disabled.
8. A private HTTPS remote without a stored credential (disable Git Credential Manager for the test): the strip shows `Git needs a user name`, then `Git needs a password` (stars; Copy does not copy it). A wrong answer ends with `Authentication failed.`. `Cancel` at the question cancels the operation and nothing changes.
9. SSH to an unknown host: the host-key question with `Trust and continue` and `Cancel`.
10. Press `Cancel` during a large fetch: the strip says `cancelling…`, then it stops, no `git.exe` is left in Task Manager, and no `*.lock` is left under `.git` (if one is, the lock banner offers to remove it).
11. Create `.git\index.lock` by hand (a leftover): the banner `Another git process is running…` appears; `Remove lock file…` asks again; `Remove lock file` deletes it and the banner goes. The question warns not to do this while another git is working.
12. Make the window narrow (about 900 px): the controls stay in one row, the path is cut with `…`, and no part of the page is clipped on the right. At 150% and 200% scale the strip and its buttons are not clipped.
